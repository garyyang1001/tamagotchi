# 10 — 動畫格式

> `specs/animations/<id>.anim.json` 的權威定義，以及 `tools/bake.py`（階段 B）
> 怎麼消費它。動畫調整一律改這個 JSON 重新烘焙，**永遠不要重新生圖**。

---

## 一、階段 B 只做四件事

```
整數像素平移  +  水平翻轉  +  z 排序  +  疊圖
```

沒有第五件。**不重新採樣、不旋轉、不縮放、不做 alpha 混合、不做非整數位移。**

這不是保守，是這一層存在的全部理由。本專案的降採樣比是 21:1
（1344×1176 → 64×56），一條腿只有 7 像素寬、眼瞼只有 3.5 像素高。
在高解析度「把後腿轉 25 度」，在輸出端的全部意義是把腿下段的 3 個像素
往旁邊挪 2 格——而挪哪幾格由降採樣格線與旋轉角度的交互作用決定，不受我們控制。
那就是閃爍，也是 Dead Cells 至今沒解掉的那個問題（見 `docs/05` 第三節）。

旋轉沒有被放棄，只是移到**階段 A**：每個姿勢只結算一次，而且要人眼核可。
階段 B 重用的是逐位元相同的像素叢集，物理上不可能閃爍。

```bash
.venv/bin/python tools/bake.py --character brown_mixed \
    --parts-dir build/pixparts \
    --anim      specs/animations/brown_mixed.anim.json \
    --out-dir   build/sheets
```

## 二、檔案骨架

```json
{
  "character_id": "brown_mixed",
  "format_version": 2,
  "defaults": { "fps": 6, "loop": false, "type": "transform" },
  "animations": [ ... ]
}
```

`defaults` 提供 `type` / `fps` / `loop` 的預設值，個別動畫可覆寫。

每個動畫共通的欄位：

| 欄位 | 必要 | 說明 |
|---|:--:|---|
| `id` | 是 | 必須對應 `firmware/include/game.h` 的 `anim_id_t` |
| `type` | | `transform`（Tier 0）或 `rig`（Tier 1 / 2） |
| `frames` | 是 | 影格數。上限見 `docs/07` 第三節，`validate.py` 會擋 |
| `frame_ms` | | **權威的時間欄位**，每格毫秒數 |
| `fps` | | 只在沒有 `frame_ms` 時用來反推（`round(1000/fps)`） |
| `loop` | | 是否循環 |
| `tier` / `desc` / `status` / `rig_parts` | | 給人看的中繼資料，bake.py 原樣抄進 atlas |

> **為什麼 `frame_ms` 是權威而不是 `fps`**：真實犬隻休息呼吸 10–30 次/分，
> 4 格的呼吸循環要 2–6 秒，換算成 fps 是 0.67–2.0 的小數。整數 fps 表達不了，
> 而寫成小數 fps 再四捨五入回毫秒，`1.33 fps` 會變成 752ms 而不是作者要的 750ms。

## 三、`type: "transform"` — Tier 0

整隻 sprite 的整數位移與水平翻轉，來源是
`art/approved/<id>/master_stand_r_64px.png`，完全不碰部件。

```json
{
  "id": "idle_breathe",
  "type": "transform",
  "tier": 0,
  "loop": true,
  "frames": 4,
  "frame_ms": 750,
  "track": [
    { "f": 0, "y":  0 },
    { "f": 1, "y": -1 },
    { "f": 2, "y": -1 },
    { "f": 3, "y":  0 }
  ]
}
```

`track` 的可用欄位：

| 欄位 | 型別 | 預設 | 說明 |
|---|---|---:|---|
| `f` | 整數 | — | 影格編號，`0 ≤ f < frames`，不可重複 |
| `x` | 整數 | 0 | 水平位移，正值往畫面右邊 |
| `y` | 整數 | 0 | 垂直位移，**負值向上** |
| `flip` | 0/1 | 0 | 水平翻轉，以畫布中線為軸 |
| `ms` | 正整數 | `frame_ms` | 這一格的顯示時間，可做不等長節奏 |

`rot` 與 `scale` **已從格式中移除**。旋轉破壞像素網格；非等比縮放讀起來是
「狗被壓扁」而不是「狗坐下」——實測把 `sit_down` 寫成 `scale_y: 86%` 就是這樣。
**坐姿是不同的剪影，不是同一個剪影變矮。**

## 四、`type: "rig"` — Tier 1 / 2

七個像素領域圖層各自的整數位移與顯示與否，再加上可選的整體變換。

```json
{
  "id": "tail_wag",
  "type": "rig",
  "tier": 1,
  "pose": "stand",
  "loop": true,
  "frames": 4,
  "frame_ms": 125,
  "layers": {
    "tail":     [ { "f": 0, "dx": 0, "dy": 0 }, { "f": 2, "dx": 2, "dy": -1 } ],
    "ear_near": [ { "f": 1, "dy": -1 } ]
  }
}
```

### 4.1 `layers`

`{ 圖層群名: 關鍵影格陣列 }`。**未列出的圖層群維持 `dx=dy=0` 且顯示。**

| 欄位 | 型別 | 預設 | 說明 |
|---|---|---:|---|
| `f` | 整數 | — | 影格編號 |
| `dx` | 整數 | 0 | 該圖層的水平位移 |
| `dy` | 整數 | 0 | 該圖層的垂直位移，負值向上 |
| `show` | 布林 | `true` | `false` 就整層不畫（眨眼的眼瞼、閉嘴時的舌頭） |

### 4.2 `pose` 與 `pose_track`

`pose` 是整個動畫的預設姿勢；`pose_track` 讓 `sit_down` 這類動畫**逐格切換姿勢**。

```json
{
  "id": "sit_down",
  "type": "rig",
  "tier": 2,
  "pose": "stand",
  "frames": 4,
  "frame_ms": 125,
  "pose_track": [
    { "f": 0, "pose": "stand" },
    { "f": 2, "pose": "sit"   }
  ],
  "layers": {
    "head": [ { "f": 2, "dy": 1 } ],
    "tail": [ { "f": 3, "dx": -1 } ]
  }
}
```

姿勢切換就是換一組圖層檔，因此**剪影可以整個換掉**——這正是 `docs/05` 撤回
「用旋轉加位移就夠」那段結論的原因：64px 上只剩剪影可讀，剪影相同就是同一個姿勢。

圖層的 `dx`/`dy` 是相對於「該姿勢的原始擺位」，所以切換姿勢不會讓位移失效。

### 4.3 整體變換

`rig` 型也可以有 `track`，欄位與 `transform` 完全相同，作用在合成完的整張影格上。
用途是「尾巴在搖，同時整隻狗在呼吸」。

## 五、關鍵影格是**步進**，不是補間

> 兩個關鍵影格之間**不做任何插值**。每一格取「`f` 小於等於它的最後一個關鍵影格」的值。

理由有兩個，都不是風格偏好：

1. **像素動畫的力量來自明確的姿勢對比。** 補間出來的中間姿勢在 64px 上讀不出來，
   只會讓動作變得軟綿綿（`docs/07` 第三節同一個理由砍掉了 55% 的影格）。
2. **補間必然產生非整數位移。** `dx` 從 0 到 3 補三格會得到 1.0 / 2.0 這種看似
   安全的值，但只要幅度不是整除就會出現 1.5，而 1.5 一定要 round——
   round 就是格線漂移，格線漂移就是閃爍。

**每個欄位各自延續自己最後出現的值**（per-field step-hold），
所以 `{"f":2,"show":false}` 不需要重寫 `dx`/`dy`。

一個 4 格的例子：

```json
"layers": { "tail": [ {"f":1,"dx":5}, {"f":2,"show":false}, {"f":3,"show":true} ] }
```

| 影格 | `dx` | `show` | 為什麼 |
|---:|---:|---|---|
| 0 | 0 | true | 還沒有任何關鍵影格，用預設值 |
| 1 | 5 | true | `f=1` 指定了 `dx` |
| 2 | 5 | false | `dx` 延續 f1，`show` 被覆寫 |
| 3 | 5 | true | `dx` 仍然延續 f1 |

## 六、七個像素領域圖層群

```
core     = shadow + torso + leg_hind_far + leg_fore_far
                 + leg_hind_near + leg_fore_near
head     = head + muzzle + eye_far + eye_near
ear_far  = ear_far
ear_near = ear_near
tail     = tail
eyelid   = eyelid
jaw      = jaw + tongue
```

**只拆真正需要獨立運動的部件，其餘合併。** 不合併的話，`--coverage 0.45` 會在
腿與軀幹的交界把兩邊都吃掉：兩者各佔該格的 30%，合成圖裡是實心，
分部件圖裡會兩邊都變透明。16 個高解析部件在像素領域收斂成 7 個。

### 6.1 檔案格式

```
build/pixparts/<character>_<pose>_<group>.png
```

三個姿勢 `stand` / `sit` / `lie` × 七個群 = 21 張。

每張都是**完整的 64×56 RGBA PNG**，角色已經在正確位置上，其餘透明。
**不裁切、不記 offset。** 這樣階段 B 的合成就只是「整數平移 + 疊圖」，
極簡到不可能對錯位。一旦允許裁切過的圖層，就得記 offset，
就得處理 offset 與位移的相加，階段 B 也就不再只是整數平移了。

alpha 只能是 0 或 255。半透明在 4bpp 索引色裡表達不了，而且會逼合成階段做
alpha 混合，混出來的中間色不在調色盤裡。

### 6.2 疊合順序

由 `art/rigs/<id>/rig.json` 的 `z` 自動推導：**群的 z = 群內成員的最大 z**。
一個群被壓平成一張圖，它必須畫在它所包含的每個部件該在的位置之上，
所以由最上面那個成員決定整群。

實際算出來（下 → 上）：

```
tail(10) < core(41) < ear_far(45) < jaw(58) < head(62) < eyelid(63) < ear_near(70)
```

合併壓平無可避免地要在兩處做取捨，這裡明寫出來，階段 A 畫圖層時要照著做：

- **`tail` 在 `core` 之下** — 尾巴被軀幹（z=30）遮住，正確。
  代價是尾巴同時被 `core` 裡的 `shadow`（z=0）遮住；陰影貼地、尾巴在空中，
  實際重疊極少，接受。
- **`jaw` 在 `head` 之下** — 下顎（z=58）低於吻部（z=60），所以張嘴時露出的部分
  在頭部下方，與吻部重疊的部分保持被遮住。正確。

`rig.json` 不存在時退回寫死的同一組順序，不會靜默改變行為。

### 6.3 以階段 A 的報告為準

`tools/assemble.py --report <path>` 會輸出它自己算的 `group_draw_order`
（窮舉七個群的 5040 種排法，挑跨群 z 反轉最少的那個）。把那份報告餵給 bake.py：

```bash
.venv/bin/python tools/bake.py -c brown_mixed \
    --assemble-report build/poses/brown_mixed.assemble.json
```

**有給就以它為準。** 階段 A 給人核可的預覽圖是照那個順序疊的，
階段 B 畫不一樣，就等於核可過的姿勢和實際烘出來的不是同一張。
兩邊不一致時 bake.py 會印出警告並列出 `rig.json` 推導的順序，不會靜默採用其中一邊。

> 實測：兩種算法在目前的 `rig.json` 上得到**完全相同**的順序，
> 而 assemble.py 額外回報了 3 組無法還原的 z 反轉
> （`tail` 被 `shadow` 蓋、`jaw` 與 `tongue` 被 `head` 蓋），
> 與 6.2 節列出的兩個取捨是同一件事。

## 七、輸出

```
build/sheets/<character>_<anim>.png        水平排列的 spritesheet
build/sheets/<character>_<anim>.json       每格的 x/y/w/h、ms、flip、pose
build/sheets/<character>_<anim>_x8.png     放大預覽（最近鄰，--scale 0 可關）
build/sheets/<character>_atlas.json        全部動畫的索引
```

索引裡每個動畫都附 `sha256_12`，可用來確認「改 JSON 重新烘焙」真的只動到該動的檔案。

## 八、硬性檢查

做不到就報錯中止，不會默默通過。

| 檢查 | 失敗訊息會指出 |
|---|---|
| 每一格只用調色盤裡的顏色 | 哪個顏色、第一次出現的座標 |
| 位移是 JSON **整數字面值** | 哪個動畫、哪一格、哪個欄位 |
| alpha 只有 0 / 255 | 哪個圖層檔、幾個半透明像素 |
| 同一動畫的所有影格尺寸一致 | 出現了哪幾種尺寸 |
| 圖層 PNG 尺寸 == 畫布尺寸 | 實際尺寸與預期尺寸 |
| 圖層檔存在 | 全部預期路徑（`--allow-missing-layers` 可放行為全透明） |
| 關鍵影格 `f` 在範圍內且不重複 | 哪個 `f` |
| track 欄位名沒打錯 | 未知欄位名與可用欄位清單 |
| `transform` 型不得有 `layers`/`pose`/`pose_track` | 哪幾個欄位放錯 |

> **連 `2.0` 都會被擋。** 數值上是整數的浮點數也要寫成整數字面值。
> 只要這個欄位可以是浮點數，遲早會有人寫 `2.5`，而 `2.5` 會在下游被某個
> `round()` 悄悄吸掉，變成看不出來的格線漂移。要擋就在最上游擋。

單一動畫失敗不會讓整批中止——bake.py 會把所有問題一次列完，
但**離開碼非零，而且不寫 atlas 索引**。下游 `pack.py` 寧可立刻找不到檔案，
也不要拿到一份看起來完整、其實缺格的資產包。要保留部分結果請加 `--keep-going`。

### 越界像素

位移把不透明像素推出畫布時，bake.py 會計數並在輸出與 atlas 裡標示，
`--strict-clip` 可以把它升級成錯誤。這是警告而不是預設錯誤，因為裁掉幾個
像素有時是刻意的（走出畫面）。

## 九、已知的尺寸矛盾

**目前 `happy` 與 `sad_wait` 會被裁切，這是資料的問題不是工具的問題。**

| 出處 | 寫的尺寸 |
|---|---|
| 本次架構契約 / `style_lock.md` | 64 × 56 |
| `art/approved/brown_mixed/master_stand_r_64px.png` 實際 | 64 × **54** |
| `specs/characters/brown_mixed.json` 的 `render.sprite_cell` | 64 × **64** |
| `docs/05` 第五節 Flash 驗算 | 64 × **53** |
| `docs/07` 第三節影格預算 | 64 × **54** |

bake.py 用 64×56 當畫布，把 64×54 的 master **水平置中、底部對齊**放進去
（偏移 `(0, 2)`，讓腳踩在同一條地平線上）。頭頂因此只剩 2 px 餘裕，於是：

```
happy     y = -7  →  141 px 被裁掉（第 1、2、3 格）
sad_wait  y = +2  →   38 px 被裁掉（全部四格）
```

三條可能的路，都要人決定，工具不猜：

1. **整體位移不烘進影格**，改由韌體繪製時偏移 blit 位置（atlas 已經逐格記了
   `dx`/`dy`，改動最小，而且省下重複的影格）。
2. **縮小幅度**：`happy` 的 -7 改成 -2 以內。彈跳的重量感會變弱。
3. **加高畫布**：但 64×56 是為了讓 1344/1176 的降採樣比是整數 21 才選的，
   改高度就要連 `style_lock.md` 的生成提示詞一起改，成本最高。

## 十一、和 `validate.py` 的分工

| 工具 | 管什麼 |
|---|---|
| `validate.py` | 21 個動畫齊不齊、影格數有沒有超預算、`rig_parts` 指到的部件存不存在 |
| `bake.py` | 資料能不能真的合成出乾淨的像素影格 |

兩邊都要過。`validate.py` 是規格層的檢查，`bake.py` 是資產層的檢查，
沒有互相取代的關係。
