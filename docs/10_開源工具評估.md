# 10 — 開源工具評估

> 這份文件回答一個該在專案開始時就問的問題：
> **`tools/` 底下這七支程式，有多少是在重造輪子？**
>
> 答案：**四支重疊，兩支不重疊，一支本來以為不該自己寫。**
> 但實測後發現，能取代它們的免費工具都不合用——
> 包括那支「不該自己寫」的 `pack.py`，實測後改判為自己寫（第四節）。

---

## 一、重疊分析

| 自製工具 | 開源對應 | 判定 |
|---|---|---|
| `pixedit.py` | Aseprite / LibreSprite | **重造輪子**。用 JSON 描述像素補丁是很糟的像素編輯器 |
| `bake.py` | Aseprite 圖層 + 影格 + CLI 匯出 | **重造輪子** |
| `preview.py` | Aseprite 內建預覽與 GIF 匯出 | **重造輪子** |
| `assemble.py` | Aseprite cel 定位 + **內建 RotSprite** | **部分重造**，且它的旋轉演算法更好 |
| `pack.py`（未寫） | `lv_img_conv`（LVGL 官方） | ~~不該自己寫~~ → **實測後改判：自己寫**，見第四節 |
| `pixelate.py` | 沒有現成的 | 自製有理 |
| `validate.py` | 沒有現成的 | 自製有理 |

### RotSprite

專案花了大量篇幅論證「旋轉會破壞像素網格」，並為此設計了兩階段烘焙。
但 **RotSprite 這個演算法早就解掉了這個問題**——先放大 8 倍、旋轉、
再猜回像素樣式，而且不引入新顏色。Aseprite 內建它。

兩階段烘焙仍然有價值（它解決的是「每格重新降採樣」而不只是旋轉），
但當初若知道 RotSprite 存在，設計會更快收斂。

### `pixelate.py` 為什麼沒有現成的

標準工具（ImageMagick `-remap`、pngquant）都是**數值最近距離**——
那正是把狗肚子吸成灰白的那個做法。

「同一個來源色在吻部要變灰、在腳要變褐」這種**區域限定的語意指派**找不到現成實作。
它之所以需要，是因為輸入是 **AI 產出的 28,000 色雜訊**，
這不是一般像素美術管線會遇到的狀況。

## 二、實測結果

### LibreSprite v1.1（免費，GPL）

從 Aseprite v1.1.7 於 2016 年分叉。macOS arm64 建置可用。

| CLI 選項 | 有無 | 用途 |
|---|:---:|---|
| `--sheet` | ✅ | 匯出 spritesheet |
| `--save-as` | ✅ | |
| `--frame-range` | ✅ | |
| **`--batch`** | ❌ | **無頭模式** |
| **`--data`** | ❌ | **匯出 JSON atlas** |
| **`--script`** | ❌ | **Lua 自動化** |
| `--split-layers` | ❌ | |
| `--list-tags` | ❌ | |

實測 `--help` **零輸出、掛住直到被砍**（exit 137）。連結 Cocoa/AppKit，永遠嘗試開視窗。

**結論：不能取代自動化管線。** `--batch`、`--data`、Lua 腳本都是 2016 年分叉**之後**
才加進 Aseprite 的，這個分支永遠不會有。

> 已安裝在 `/Applications/libresprite.app`。**當 GUI 像素編輯器用是完全合格的**，
> 見第三節。

### Pixelorama 1.2（免費，Godot）

`--help` 零輸出，只開 GUI。**無頭自動化不可行。**
（另註：homebrew 已標記為 deprecated，2026-09-01 起停止提供，因為過不了 macOS Gatekeeper。）

### Aseprite（$20，原始碼公開但非 OSI 授權）

具備全部需要的：`-b/--batch`、`--sheet`、`--data`、`--script`（Lua）、
`--split-layers`、`--list-tags`、RotSprite。

**未實測**——需要購買或自行編譯（編譯需要 Skia，環境還缺 `cmake` 與 `ninja`）。
任何關於它的敘述都應視為未經本專案驗證。

## 三、結論與現行決策

**保留現有管線，加上 LibreSprite 當手動修圖工具。**

理由：

1. **能取代管線的只有 Aseprite，而它未經驗證且要付費。**
   現有管線七支工具、59 項自我測試全過、可重現性逐位元相同。
   在沒有實測過的替代品面前拆掉它是不理性的。

2. **目前三個未解缺陷都是手動修圖問題，不是管線問題。**

   | 缺陷 | 為什麼管線解不了 | LibreSprite 怎麼解 |
   |---|---|---|
   | `chase_ball` 四條腿不動 | 腿併在 `core` 圖層 | 把腿各自拉成獨立圖層 |
   | 趴姿前腿與胸口有 6px 洞 | 高解析原圖就是分離的 | 筆刷補三筆 |
   | `sleep_breathe` 同上 | 同上 | 同上 |

   這些用免費的 LibreSprite 今天就能修，不需要動管線。

3. ~~**`pack.py` 不要自己寫。**~~ **已於 2026-08-02 實測，改判為自己寫**，理由見第四節。
   簡短版：npm 版強制自適應量化、會打亂我們手工排的索引順序；Python 版雖然
   100% 保真，但保真的前提是「你先自己做出索引 PNG」——而那正是唯一難的一步。

## 四、`lv_img_conv` 實測（2026-08-02）

第三節留了一句「`pack.py` 不要自己寫，先評估 `lv_img_conv`」。這一節把它做完。

**結論先講：(c) 整包自己寫。** 兩個版本都試過、都跑起來了，
但它們合起來只覆蓋 `pack.py` 的一個步驟，而那個步驟是一行 `png.pack_rows()`。

### 4.1 裝得起來嗎

| 版本 | 來源 | 能不能跑 |
|---|---|---|
| npm `lv_img_conv@0.4.0` | LVGL 官方，MIT，2025 年後未更新 | **要修三個相依才跑得動** |
| Python `LVGLImage.py` | lvgl/lvgl `scripts/`（v9） | 裝 `pypng` 就能跑 |

PyPI 上**沒有** `lv_img_conv` 這個套件（`pip index versions lv_img_conv` → no matching
distribution）。所謂「Python 版」是 lvgl 主 repo 裡的 `scripts/LVGLImage.py`，要用 curl 抓。

npm 版開箱是壞的，依序踩到三個坑：

```
1. canvas@2.8 在 node 22 / darwin-arm64 沒有預編譯檔，回退原始碼編譯
   → gyp: Call to 'pkg-config pixman-1 --libs' returned exit status 127
   解法：npm overrides 指定 canvas@3.2.0（有預編譯檔）
2. ts-node 是 runtime 相依，但 typescript 不是（被放在 devDependencies）
   → TypeError: Cannot read properties of undefined (reading 'fileExists')
3. 它的 tsconfig 指定 transpiler: ts-node/transpilers/swc，@swc/core 也只在 devDependencies
   → Error: swc compiler requires either @swc/core or @swc/wasm
```

修好三個之後 `--help` 正常。完整可重現的安裝：

```bash
npm init -y
# package.json 加 "overrides": { "canvas": "3.2.0" }
npm install lv_img_conv@0.4.0 typescript@4.9.5 @swc/core@1.3.100
```

> 這和 LibreSprite 那條是同一類發現：**光讀 README 不會知道它裝不起來。**

### 4.2 它能不能吃我們的調色盤

**這是決定性的一題，兩個版本的答案完全相反。**

#### npm 版：不能，而且沒有開關可以關掉

`--help` 的完整選項只有 `-o -f -i -c -t --binary-format -s -d`，**沒有 `--palette`**。
原始碼 `lib/convert.ts:110-127` 對任何 `CF_INDEXED_*` 都無條件呼叫
`buildPalette(..., { colors: 16 })`（image-q 的自適應量化），沒有任何分支可以繞過。

實測把「已經照我們的順序索引好的 PNG」餵給它，它仍然重新量化並打亂順序：

| 我們的索引 | 語意 | 期望 | npm 版實得 |
|---:|---|---|---|
| 0 | transparent | `#000000` a=0 | `#D3A896` a=255 **不透明** |
| 1 | outline | `#3A3229` | `#BC8E7E` |
| 5 | floor_shade | `#B6A085` | `#B4ACA0` |
| 9 | wood_light | `#B08D66` | `#C2D8E6` |

前 10 個索引只有 4 個落在正確位置。**連 index 0 = 透明都保不住**——
而我們整個 RLE 格式（`0nnnnnnn` = 透明連續）就建立在那條約定上。

更嚴重的是它是**逐圖各自量化**，於是：

- 同一角色的 21 個動畫會拿到 21 份**不同排列**的調色盤，
  `index[]` 裡的 `palette_id` 直接失去意義。
- **日夜換盤壞掉。** `specs/palettes/scene.json` 明寫「日夜共用同一張點陣圖，
  只換調色盤」，那要求 `room_day` 與 `room_night` 產生**逐位元相同的索引平面**。實測：

  | | 索引平面相同的像素 | 套上夜間盤後與真正 room_night 不符 |
  |---|---:|---:|
  | 專案手工調色盤 | 56320/56320（100.00%） | 0（0.00%） |
  | npm `lv_img_conv` | 40989/56320（72.78%） | **15331（27.22%）** |

  27% 的像素會變成錯的顏色。這條路直接封死。

#### Python 版：可以，100% 保真——但有前提

`LVGLImage.py:940` 的邏輯是：**如果輸入 PNG 本身就有調色盤、而且長度剛好等於
`2**bpp`（I4 就是 16），它就原封不動沿用 PNG 的 PLTE + 索引值。**

實測 94 個資產全部通過：

```
檢查 94 個檔案：調色盤不符 0 個，索引平面不符 0 個
-> 調色盤與索引順序 100% 保真
```

**但前提是我們得先自己做出那個 16 色索引 PNG。** 直接餵 `build/sheets/` 的
RGBA 原檔，它會走 `PngQuant` 分支：

```
BaseException: cannot find pngquant tool, install it via ... `brew install pngquant`
```

而且就算裝了 `pngquant`，那也是**自適應量化**——回到 npm 版一模一樣的失敗。
所以「RGBA → 我們的 16 色索引平面」這一步**無論如何都得我們自己寫**，
它正好就是整個 `pack.py` 裡唯一有語意難度的部分。

### 4.3 它輸出什麼、壓縮率如何

指定的兩個測試檔，以及全部 94 個資產（84 張 spritesheet + 10 張場景圖，
共 1,542,829 px）：

```bash
# npm 版
lv_img_conv room_day.png -c CF_INDEXED_4_BIT -t bin -o room_day.bin -f
# Python 版（輸入必須是已索引的 16 色 PNG）
python LVGLImage.py --ofmt BIN --cf I4 --compress {NONE,RLE,LZ4} -o out/ idxpng/
```

**單檔：**

| 方案 | `brown_mixed_walk` 256×56 | `room_day` 320×176 |
|---|---:|---:|
| 4bpp 未壓縮（基準） | 7,168 B | 28,160 B |
| npm `lv_img_conv`（無壓縮） | 7,236 B | 28,228 B |
| `LVGLImage.py --compress NONE` | 7,244 B | 28,236 B |
| `LVGLImage.py --compress RLE` | — | 7,523 B |
| `LVGLImage.py --compress LZ4` | — | 1,395 B |
| **我們的自訂 RLE** | **2,966 B** | **4,785 B** |

> `room_day` 自訂 RLE = 4,785 B 已獨立重現，與先前量到的數字完全相同
> （條件：同色 token 上限 15 像素、且 run 不跨列）。

**全部 94 個資產的純像素酬載**（已扣掉每檔的 LVGL header 12 B + 調色盤 64 B + 壓縮頭 12 B）：

| 方案 | 大小 | 壓縮率 | 相對自訂 RLE |
|---|---:|---:|---:|
| 4bpp 未壓縮 | 771,419 B | 1.00× | 3.03× |
| `LVGLImage.py` RLE | 515,294 B | 1.50× | **2.02× 更差** |
| **自訂 RLE** | **254,779 B** | **3.03×** | 1.00× |
| `LVGLImage.py` LZ4 | 227,881 B | 3.39× | 0.89×（好 10.6%） |

兩件事值得記下來：

1. **LVGL 的 RLE 比我們的差一倍。** 它是位元組導向、`threshold=16`
   （少於 16 個重複就整段原樣存），而且**沒有針對透明做優化**。
   我們的格式把索引直接編進控制位元組、透明一個 token 吃 127 像素，
   對「大片透明 + 平塗」這種素材本來就佔便宜。
2. **LZ4 比我們好 10.6%，但那不重要。** `assets` 分區有 6 MB，
   組完 `assets.bin` 之後：

   | | 總計 | 佔 6 MB 分區 |
   |---|---:|---:|
   | 自訂 RLE | 256,807 B（250.8 KB） | 4.08% |
   | LVGL LZ4 | 229,909 B（224.5 KB） | 3.65% |

   差距 26,898 B = **分區的 0.43%**。為了 0.43% 的 flash 去換一個
   「必須整張解壓、不能逐列隨機存取、韌體要多帶一個 LZ4 解碼器」的格式，不划算。
   **壓縮率不是這個專案的約束條件**，選格式該看解碼成本與複雜度。

### 4.4 它知不知道動畫與 atlas

**完全不知道，而且不是「支援得不好」，是這一層根本不存在。**

兩個版本的原始碼對 `animation` / `atlas` / `frame` / `sprite` / `spritesheet`
的命中數都是 **0**。它們的心智模型是「一張圖 → 一個 `lv_img_dsc_t`」，
一次一張、各自獨立，沒有封裝檔的概念。

我們需要而它們一概沒有的：

| 需求 | 我們的來源 | lv_img_conv |
|---|---|---|
| 單一封裝檔 + `name_hash` 索引 | docs/04 D 節 | ✗ 每張圖一個獨立 .bin |
| 角色共用一組調色盤（`palette_id`） | `specs/palettes/*.json` | ✗ 每張圖各嵌 64 B 調色盤 |
| RGB565 調色盤（32 B/組） | docs/04 | ✗ 固定 ARGB8888（64 B/組） |
| `frame_count` / 每格 `ms` | `build/sheets/*_atlas.json` | ✗ |
| 每格 `screen_dx` / `screen_dy` / `flip` | `build/sheets/<char>_<anim>.json` | ✗ |
| 84 個動畫、332 格的組織結構 | `bake.py` 產出 | ✗ |

### 4.5 結論：(c) 整包自己寫

三個選項對照：

| | 判定 |
|---|---|
| (a) 直接用，只寫薄索引產生器 | **不可行**。npm 版會毀掉調色盤語意與日夜換盤；Python 版不吃我們的 RGBA 輸入 |
| (b) 用它做 PNG → 4bpp 索引點陣圖，自己寫 RLE 與封裝 | **不划算**，見下 |
| **(c) 整包自己寫** | **採用** |

**(b) 為什麼不划算**：它負責的那一段其實不是「PNG → 索引點陣圖」，
而只是「**已索引的** PNG → 打包成 nibble」。前半段（RGBA → 我們的 16 色索引平面）
它做不到，得我們自己寫；而後半段用 `pypng` 是一行 `png.pack_rows(rows, 4)`。
走 (b) 等於：自己做索引 PNG → 開 subprocess → 再寫一個 LVGL bin 解析器把索引平面撈回來
→ 才能開始做我們自己的 RLE 與封裝。**比直接寫還多三個步驟和一個外部相依。**

`pack.py` 要做的事，以及 `lv_img_conv` 覆蓋了多少：

| # | 步驟 | 誰做 |
|---|---|---|
| 1 | RGBA PNG → 我們手工調色盤的索引平面（含日夜共用平面） | **我們**（唯一有語意難度的一步） |
| 2 | 索引平面 → 4bpp 打包 | 它可以，但 `png.pack_rows()` 也是一行 |
| 3 | 自訂 RLE 壓縮 | **我們**（它的 RLE 差一倍，格式也不同） |
| 4 | header + `index[]` + `name_hash` + RGB565 調色盤表 + blobs | **我們**（它沒有封裝檔概念） |
| 5 | 把 `frame_count` / `ms` / `screen_dx/dy` 帶進韌體讀得到的形式 | **我們** |
| 6 | 逐位元可重現（`REBUILD.sh` 的硬性要求） | 兩者都是決定性的，實測跑兩次雜湊相同 |

**六步裡它只覆蓋第 2 步，而第 2 步是一行。**

### 4.6 順手撿到的：`docs/04` 的 RLE token 版面塞不進 1 byte

docs/04 D 節寫的是：

```
1nnnniiii         接下來 n 個像素都是索引 i（n = 1..15）
```

`1` + `nnnn`(4 bit) + `iiii`(4 bit) = **9 bit**，一個位元組放不下。
（`0nnnnnnn` 那條沒問題。）先前量到的 4,785 B 對應的是「n 上限 15」的 token 數，
所以那個數字是對的，只是**版面需要重寫**。

實測幾種真的塞得進 8 bit 的版面（全部逐列，run 不跨列）：

| 版面 | 全部 94 個資產 | 壓縮率 | `room_day` |
|---|---:|---:|---:|
| docs/04 字面版（9 bit，無法實作） | 254,779 B | 3.03× | 4,785 B |
| `1nnniiii`，同色上限 7 | 277,257 B | 2.78× | 8,849 B |
| **`1nnniiii` + 逃脫位元組，同色上限 255** | **259,421 B** | **2.97×** | **2,478 B** |
| 高 nibble = n(1..15)、低 nibble = index | 295,528 B | 2.61× | 4,785 B |

**建議採用逃脫版**：

```
0nnnnnnn            接下來 n 個像素透明        n = 1..127
1nnniiii            接下來 n 個像素是索引 i     n = 1..7
1000iiii + <count>  接下來 count 個像素是索引 i  count = 8..255
```

它是唯一同時滿足「塞得進 8 bit」與「不比字面版差」的：整體只差 1.8%，
而在大片平塗的房間底圖上**反而好一倍**（2,478 B vs 4,785 B，壓縮 11.4×），
因為 320 px 寬的牆面連續不必再被切成每 15 像素一段。

另外，**run 不跨列是刻意的**，代價只有 2.3%（逐列 254,779 vs 跨列 249,046），
換到的是可以對每一列建索引、支援局部重繪。

## 五、給未來的教訓

> **開工前先查有沒有現成的。**

這個評估該在專案第一天做，而不是在寫完七支工具、跑完數十輪迭代之後。
代價是重造了四支工具，以及繞遠路重新發現了 RotSprite 早已解決的問題。

減損因素：即使當初就查了，結論仍會是「免費的都不合用」——
因為擋路的是 LibreSprite 缺 `--batch`，那不是查資料就會知道的，
要實際下載跑過才會發現。所以真正的教訓不是「查文件」，是**「早點實測」**。

`lv_img_conv` 的評估（第四節）是同一課的第二次上：
這份文件先前寫「`pack.py` **不該自己寫**」，那句話是**只讀 README 推論出來的**——
README 說它支援 I1/I2/I4/I8 索引色，聽起來正是我們要的。
實測才發現關鍵在「它從哪裡拿調色盤」，而 README 對此一字未提。
