# 04 — 資料結構與存檔設計

第一版是純單機，所以「資料庫」在這個專案裡指的是**裝置端的三層資料結構**，
不是 SQL。ESP32 上沒有有意義的 SQL 資料庫，硬塞一個進去只會浪費 flash 與 RAM。

| 層 | 位置 | 生命週期 | 用途 |
|---|---|---|---|
| A 執行期狀態 | RAM | 開機到關機 | 遊戲邏輯讀寫的即時狀態 |
| B 存檔 | flash `savegame` 分區 | 永久 | 養成進度。**掉電絕不可損毀** |
| C 事件記錄 | LittleFS 環形檔 | 永久（滾動覆蓋） | 成長紀錄、除錯、未來的家長功能 |
| D 資產包 | flash `assets` 分區 | 燒錄時寫入 | 唯讀，`spi_flash_mmap` 直接定址 |

## A. 執行期狀態（RAM）

```c
typedef enum {
    CHAR_ICE_PRINCESS = 0,
    CHAR_CHIHUAHUA    = 1,
    CHAR_BROWN_MIXED  = 2,
    CHAR_BRINDLE_GUARD= 3,
    CHAR_COUNT        = 4
} character_id_t;

/* 需求值一律 0..100。用 uint8_t 而非 float：
   ESP32-S3 有 FPU，但存檔要 packed 且版本穩定，整數比較好對齊與遷移。 */
typedef struct {
    uint8_t hunger;      /* 飽足 */
    uint8_t energy;      /* 精力 */

    uint8_t bladder;     /* 如廁，僅狗 */
    uint8_t tidy;        /* 整潔，僅公主 */

typedef struct {
    needs_t  needs;
    uint16_t affection;      /* 只增不減，上限 65535 */
    uint8_t  outfit_id;      /* 僅公主 */
    uint8_t  current_anim;   /* animation_id_t */
    uint16_t anim_frame;
    uint32_t anim_started_ms;
    int16_t  pos_x, pos_y;   /* 螢幕座標 */
    uint8_t  facing;         /* 0 = 面向右，1 = 面向左 */
    uint8_t  flags;
} character_runtime_t;

typedef struct {
    character_runtime_t chars[CHAR_COUNT];
    uint32_t  now_unix;
    uint8_t   night_mode;
    uint8_t   selected_char;   /* 目前被小孩點選的角色，0xFF = 無 */
    uint8_t   brightness;
    uint8_t   volume;
    bool      dirty;           /* 有未存檔的變更 */
    uint32_t  last_save_ms;
} game_state_t;
```

## B. 存檔

### 為什麼不用 NVS

NVS 可以用，但 blob 改寫較重，且磨損平衡的行為對我們是黑箱。
自管一個 8 KB 分區、手動做 A/B 雙槽，換來的是**可稽核的掉電安全性**——
這對一台會被 3 歲小孩隨手拔電的裝置是必要的，不是過度設計。

NVS 仍然保留，但只放設定值（亮度、音量），那些丟了無所謂。

### 結構

```c
#define SAVE_MAGIC    0x31544550u   /* "PET1" little-endian */
#define SAVE_VERSION  1
#define SAVE_SLOT_SZ  4096          /* 一個 flash sector */

typedef struct __attribute__((packed)) {
    needs_t  needs;
    uint16_t affection;
    uint8_t  outfit_id;
    uint8_t  unlocked_outfits;   /* bitmask */
    uint8_t  reserved[4];
} character_save_t;               /* 13 bytes */

typedef struct __attribute__((packed)) {
    uint32_t magic;
    uint16_t version;
    uint16_t size;               /* 本結構實際大小，用於版本遷移 */
    uint32_t seq;                /* 單調遞增。開機時選 seq 較大且 CRC 正確者 */
    uint64_t saved_at_unix;

    character_save_t chars[CHAR_COUNT];

    uint32_t total_feeds;
    uint32_t total_plays;
    uint32_t total_pets;
    uint32_t first_boot_unix;    /* 「我們認識多久了」 */

    uint8_t  brightness;
    uint8_t  volume;
    uint8_t  night_start_hour;   /* 預設 20 */
    uint8_t  night_end_hour;     /* 預設 7  */

    uint8_t  reserved[32];       /* 預留給未來欄位，避免馬上就要 v2 */
    uint32_t crc32;              /* 涵蓋本結構前面所有位元組 */
} save_blob_t;
```

### A/B 雙槽

```
savegame 分區 8 KB
├── slot A  offset 0      4 KB
└── slot B  offset 4096   4 KB
```

**寫入**：永遠寫進 `seq` 較小的那一槽（也就是較舊的），寫完驗證 CRC。
過程中掉電最多毀掉舊槽，新槽仍完好。

**讀取**：兩槽都讀，取 `magic` 正確、`crc32` 通過、`seq` 最大者。
兩槽都壞才回到出廠預設——而且**出廠預設是「四個角色都很開心」**，不是全部歸零。

### 寫入時機與 flash 壽命

| 時機 | 說明 |
|---|---|
| 定期 | 有 `dirty` 且距上次寫入 ≥ **300 秒** |
| 立即 | 進入 deep sleep 前、偵測到電量過低、解鎖里程碑、換裝 |

壽命估算：

```
每天寫入 ≈ 60 次（清醒 5 小時 / 300 秒 + 事件觸發）
雙槽交替 → 每槽每天 30 次
flash 耐久 100,000 次 ÷ 30 ≈ 3,300 天 ≈ 9 年
```

### 版本遷移

**改動 `save_blob_t` 的任何欄位都必須遞增 `SAVE_VERSION` 並寫遷移函式。**
小孩的養成進度不可以因為韌體更新就消失。這件事沒有商量餘地。

`reserved[32]` 的存在就是為了讓「加欄位」不需要換版本——
新欄位從 reserved 裡切，舊韌體讀到的是 0，新韌體讀舊檔也是 0，雙向相容。

## C. 事件記錄

固定長度記錄的環形檔，寫在 LittleFS。

```c
typedef enum {
    EV_BOOT = 1, EV_SLEEP, EV_WAKE,
    EV_FEED, EV_PLAY, EV_PET, EV_TOILET,
    EV_DRESS, EV_UNLOCK, EV_MILESTONE,
    EV_NEEDS_SNAPSHOT,      /* 每小時一筆，用於畫成長曲線 */
} event_type_t;

typedef struct __attribute__((packed)) {
    uint32_t ts;        /* unix time */
    uint8_t  type;      /* event_type_t */
    uint8_t  actor;     /* character_id_t，非角色事件填 0xFF */
    uint8_t  value;     /* 依 type 解讀，例如餵食回補量 */
    uint8_t  flags;
    uint32_t extra;     /* 依 type 解讀 */
    uint32_t reserved;
} event_rec_t;          /* 16 bytes，對齊友善 */
```

```
events.bin
├── header 16 B  { magic, version, capacity, write_index }
└── records      capacity × 16 B，寫滿後從頭覆蓋
```

`capacity = 8192` → 128 KB 檔案 → 以每天約 60 筆計，**約 136 天**的完整歷史。

用途：
- 未來若要做家長回顧（「這個月餵了幾次」），資料已經在了
- 除錯時可以重建小孩實際的操作序列
- `EV_NEEDS_SNAPSHOT` 讓「和牠們認識了 87 天」這種畫面有資料來源

**不含任何個人資料。** 只有時間戳與遊戲事件，沒有姓名、沒有位置、不連網。

## D. 資產包

由 `tools/pack.py` 產出，自我測試在 `tools/test_pack.py`。
`lv_img_conv` 的兩個版本都實測否決了，理由見 `docs/10` 第四節。

```
data/assets.bin                                    實測 213,156 B（208.2 KB）
├── header        48 B                             檔頭，固定長度
├── assets[102]   102 × 20 B = 2,040 B             一個動畫／一張圖一列，照 name_hash 排序
├── frames[365]   365 × 16 B = 5,840 B             逐格的時間與位移，照資產順序連續
├── palettes[10]  10 × 32 B = 320 B                16 色 RGB565，角色日／夜各一組
└── blobs         204,908 B                        4bpp 索引點陣圖，逐格 RLE
```

燒進 `assets` 分區後用 `spi_flash_mmap` 映射到位址空間，
三張表可以直接當 C 結構陣列存取、零複製（欄位全部自然對齊，沒有隱含 padding，
所以**不需要** `__attribute__((packed))`——packed 會讓 Xtensa 產生逐位元組讀取）。
sprite 用到時才 RLE 解碼進 PSRAM 的 LRU 快取。

### D.1 檔頭

一律小端序。`content_crc32` 涵蓋檔頭之後的所有位元組。

| 位移 | 型別 | 欄位 | 說明 |
|---:|---|---|---|
| 0 | `char[4]` | `magic` | `"IPA1"` |
| 4 | `uint16` | `version` | 目前 1。不相容的改動要遞增 |
| 6 | `uint16` | `header_bytes` | 48。舊韌體讀新檔時用它跳過檔頭 |
| 8 | `uint16` | `asset_count` | 102 |
| 10 | `uint16` | `frame_count` | 365 |
| 12 | `uint16` | `palette_count` | 10 |
| 14 | `uint16` | `flags` | bit0 = blob 單位是每格影格；bit1 = 相同 blob 已去重 |
| 16 | `uint32` | `asset_offset` | 48 |
| 20 | `uint32` | `frame_offset` | 2,088 |
| 24 | `uint32` | `palette_offset` | 7,928 |
| 28 | `uint32` | `blob_offset` | 8,248 |
| 32 | `uint32` | `blob_bytes` | 204,908 |
| 36 | `uint32` | `total_bytes` | 213,156 = 整個檔案 |
| 40 | `uint32` | `content_crc32` | zlib CRC-32，涵蓋 `[48, total_bytes)` |
| 44 | `uint32` | `reserved` | 0 |

### D.2 資產表

**照 `name_hash` 遞增排序**，韌體可以二分搜尋。
名稱是 FNV-1a 32 bit，例如 `"brown_mixed/walk"` → `0xFCE6C829`。
命名規則：角色動畫 `<character_id>/<anim_id>`、房間 `scene/room`、物件 `obj/<key>`。
`data/assets.json` 是完整的名字 → 雜湊對照表。

| 位移 | 型別 | 欄位 | 說明 |
|---:|---|---|---|
| 0 | `uint32` | `name_hash` | FNV-1a 32。**打包時檢查碰撞，撞到直接中止** |
| 4 | `uint32` | `frame_index` | 影格表的起始位置 |
| 8 | `uint16` | `frame_count` | 影格數 |
| 10 | `uint16` | `w` | 一格的寬 |
| 12 | `uint16` | `h` | 一格的高 |
| 14 | `uint8` | `palette_day` | 日間調色盤 id |
| 15 | `uint8` | `palette_night` | 夜間調色盤 id |
| 16 | `uint8` | `type` | 0 = 角色動畫、1 = 房間底圖、2 = 場景物件 |
| 17 | `uint8` | `flags` | bit0 = `loop` |
| 18 | `uint16` | `reserved` | 0 |

### D.3 影格表

| 位移 | 型別 | 欄位 | 說明 |
|---:|---|---|---|
| 0 | `uint32` | `blob_offset` | **相對檔案開頭**的絕對位移，mmap 之後直接加 base |
| 4 | `uint32` | `blob_bytes` | RLE 位元組數 |
| 8 | `uint16` | `ms` | 這一格停留幾毫秒（動畫定義用不等長影格，見 docs/11） |
| 10 | `int8` | `screen_dx` | 繪製時的水平偏移 |
| 11 | `int8` | `screen_dy` | 繪製時的垂直偏移 |
| 12 | `uint8` | `flip` | **只是紀錄**：這一格的像素已經是鏡像的，渲染層不要再翻一次 |
| 13 | `uint8[3]` | `reserved` | 0 |

`screen_dx/dy` 是 transform 型動畫的全部內容——呼吸、難過等待、跳躍
都是同一張點陣圖配不同的偏移量。這也是去重能省下 24.7% 的原因（見 D.5）。

### D.4 調色盤

每組 16 × `uint16` RGB565（32 B），來源是 `specs/palettes/*.json`，
轉換是 `(r>>3)<<11 | (g>>2)<<5 | b>>3`。
**index 0 一律是透明**——RLE 的 `0nnnnnnn` token 建立在這條約定上，
`pack.py` 會擋掉把透明放在其他索引的調色盤。

夜間不是把顏色調暗，是**換一組調色盤**：同一張點陣圖 + 另外 32 B。
房間更進一步——`room_day` 與 `room_night` 的索引平面逐位元相同，
所以整個房間日夜共用**一份** blob。`pack.py` 會驗證這件事，不同就中止。

### D.5 blob 的單位：每格影格

兩種都實作過、都量過（`pack.py --blob-unit` 可以切換，每次執行都印對照表）。
102 個資產、365 格、1,489,712 個像素（解碼欄只計多格資產的 91 個）：

| 方案 | 全部 blob | 壓縮率 | 解一格要解碼的像素（平均／最大） |
|---|---:|---:|---:|
| 每張 spritesheet | 257,718 B | 2.89× | 15,690 / 36,864 |
| 每格影格 | 272,258 B | 2.74× | 3,993 / 6,144 |
| **每格影格 + 相同 blob 去重** | **204,908 B** | **3.64×** | **3,993 / 6,144** |

直覺會以為 per-sheet 比較小（一列橫跨四格，透明 run 可以接起來），
量出來也確實小 5.3%。**但那個優勢被去重整個吃掉還倒賠 20%。**

原因是 transform 型動畫把位移記在 `screen_dy` 而不是畫進像素裡——
同一個動畫的四格是**逐位元相同的點陣圖**。365 格裡只有 280 格是唯一的，去重省 24.7%。
而去重只有在 blob 是「每格」時才做得到：blob 是整張 sheet 的話，四格黏在一起。

決定性的那一項是解碼成本：渲染層一次只畫一格，per-sheet 要多解 **3.93 倍**的
像素、佔 3.93 倍的 PSRAM（公主一張 sheet 是 36,864 px，一格只要 6,144）。
兩個軸都輸，所以預設是每格影格。

### D.6 RLE 格式

針對 4bpp 索引 + 大片透明區最佳化：

```
0nnnnnnn            接下來 n 個像素透明          n = 1..127
1nnniiii            接下來 n 個像素是索引 i      n = 1..7
1000iiii + <count>  接下來 count 個像素是索引 i  count = 8..255（2 bytes）
```

**run 不跨列。** 代價 2.3%（逐列 254,779 B vs 跨列 249,046 B），
換到的是可以對每一列建索引、支援局部重繪。
解碼器可以拿「run 跨列」當格式錯誤來擋——`test_pack.py` 就是這樣做的。

> **2026-08-02 修正。** 這裡原本寫的是 `1nnnniiii`——
> `1` + `nnnn`(4 bit) + `iiii`(4 bit) = **9 bit，一個位元組放不下**，
> 這條規格從來沒有辦法實作。寫 `pack.py` 之前評估 `lv_img_conv` 時才發現
> （見 `docs/10` 第 4.6 節）。
>
> 逃脫版是量過的三個候選裡唯一同時滿足「塞得進 8 bit」與「不比原本的字面版差」的：
>
> | 方案 | 全部 94 張 | 壓縮率 | `room_day` |
> |---|---:|---:|---:|
> | 原字面版（9 bit，無法實作） | 254,779 B | 3.03× | 4,785 B |
> | `1nnniiii`，同色上限 7 | 277,257 B | 2.78× | 8,849 B |
> | **逃脫版（上表）** | **259,421 B** | **2.97×** | **2,478 B** |
>
> 整體只差 1.8%，而在大片平塗的房間底圖上**反而好一倍**——
> 320 px 寬的牆面連續不必再被切成每 15 像素一段。

實測這種平塗、限色、大片透明的像素藝術，壓縮率約 **3×**（加去重是 3.64×）。
（LVGL 內建的 RLE 在同一批資產上是 1.50×，我們的格式好 2.02 倍；
LZ4 是 3.39×，只好 10.6%，換算到 6 MB 分區是 4.08% → 3.65%，不值得引進相依。）

### D.7 韌體端的結構定義

可以直接貼進 `firmware/include/assets.h`。
**不要加 `__attribute__((packed))`**：欄位本來就自然對齊，
加了只會讓編譯器對 mmap 出來的資料產生逐位元組讀取。

> 這段不是憑空寫的：抽出來用 `cc -std=c11 -Wall -Wextra` 編過、
> 直接讀真的 `data/assets.bin`，四個資產 15 格解出來的像素
> 和 `tools/test_pack.py` 的 Python 解碼器**逐位元組相同**。
> 四個 `_Static_assert` 也是這樣才有意義——它們在編譯期擋下
> 「有人改了 Python 這邊的版面卻沒改 C」。

```c
#include <stdint.h>

#define IPA_MAGIC          "IPA1"
#define IPA_VERSION        1

/* header flags */
#define IPA_HF_BLOB_PER_FRAME  (1u << 0)   /* blob 的單位是每格影格 */
#define IPA_HF_BLOB_DEDUP      (1u << 1)   /* 相同的 blob 已合併 */

/* asset flags */
#define IPA_AF_LOOP            (1u << 0)

typedef enum {
    IPA_TYPE_ANIM   = 0,        /* 角色動畫 */
    IPA_TYPE_SCENE  = 1,        /* 房間底圖 */
    IPA_TYPE_OBJECT = 2,        /* 場景物件 */
} ipa_type_t;

typedef struct {                /* 48 bytes */
    char     magic[4];          /* "IPA1" */
    uint16_t version;
    uint16_t header_bytes;
    uint16_t asset_count;
    uint16_t frame_count;
    uint16_t palette_count;
    uint16_t flags;
    uint32_t asset_offset;
    uint32_t frame_offset;
    uint32_t palette_offset;
    uint32_t blob_offset;
    uint32_t blob_bytes;
    uint32_t total_bytes;
    uint32_t content_crc32;     /* 涵蓋 [header_bytes, total_bytes) */
    uint32_t reserved;
} ipa_header_t;

typedef struct {                /* 20 bytes */
    uint32_t name_hash;         /* FNV-1a 32，表照它遞增排序 */
    uint32_t frame_index;
    uint16_t frame_count;
    uint16_t w;
    uint16_t h;
    uint8_t  palette_day;
    uint8_t  palette_night;
    uint8_t  type;              /* ipa_type_t */
    uint8_t  flags;             /* IPA_AF_* */
    uint16_t reserved;
} ipa_asset_t;

typedef struct {                /* 16 bytes */
    uint32_t blob_offset;       /* 相對檔案開頭 */
    uint32_t blob_bytes;
    uint16_t ms;
    int8_t   screen_dx;
    int8_t   screen_dy;
    uint8_t  flip;              /* 像素已鏡像，不要再翻 */
    uint8_t  reserved[3];
} ipa_frame_t;

typedef struct {                /* 32 bytes */
    uint16_t rgb565[16];        /* index 0 一律是透明 */
} ipa_palette_t;

_Static_assert(sizeof(ipa_header_t)  == 48, "檔頭版面和 docs/04 D 節不符");
_Static_assert(sizeof(ipa_asset_t)   == 20, "資產表版面和 docs/04 D 節不符");
_Static_assert(sizeof(ipa_frame_t)   == 16, "影格表版面和 docs/04 D 節不符");
_Static_assert(sizeof(ipa_palette_t) == 32, "調色盤版面和 docs/04 D 節不符");

/* 名稱雜湊。和 tools/pack.py 的 fnv1a_32 必須完全一致。 */
static inline uint32_t ipa_hash(const char *s)
{
    uint32_t h = 0x811C9DC5u;
    while (*s) { h ^= (uint8_t)*s++; h *= 0x01000193u; }
    return h;
}

/* 二分搜尋。assets 是照 name_hash 遞增排序的。 */
static inline const ipa_asset_t *ipa_find(const ipa_asset_t *a, uint16_t n,
                                          uint32_t hash)
{
    uint16_t lo = 0, hi = n;
    while (lo < hi) {
        uint16_t mid = (uint16_t)((lo + hi) >> 1);
        if (a[mid].name_hash < hash)      lo = (uint16_t)(mid + 1);
        else if (a[mid].name_hash > hash) hi = mid;
        else                              return &a[mid];
    }
    return NULL;
}

/* RLE 解碼成 8bpp 索引平面（一列一列，run 不跨列）。
   回傳實際填出來的列數，不等於 h 就是資料壞了。 */
static inline int ipa_rle_decode(const uint8_t *p, uint32_t n,
                                 uint8_t *dst, int w, int h)
{
    int row = 0, col = 0;
    uint32_t i = 0;
    while (i < n && row < h) {
        uint8_t b = p[i++];
        int cnt, idx;
        if (b & 0x80) {
            idx = b & 0x0F;
            cnt = (b >> 4) & 0x07;
            if (cnt == 0) {                 /* 1000iiii + <count> */
                if (i >= n) return -1;
                cnt = p[i++];
            }
        } else {                            /* 0nnnnnnn 透明 */
            idx = 0;
            cnt = b & 0x7F;
            if (cnt == 0) return -1;
        }
        if (col + cnt > w) return -1;       /* run 跨列 = 格式壞了 */
        for (int k = 0; k < cnt; k++) dst[row * w + col + k] = (uint8_t)idx;
        col += cnt;
        if (col == w) { col = 0; row++; }
    }
    return (col == 0) ? row : -1;
}
```

## 完整性檢查清單

實作存檔層時逐項驗證，這些是掉電安全性的實際保證：

- [ ] 寫入前先 erase 目標 sector，寫完立刻讀回驗證 CRC
- [ ] 驗證失敗不更新 `seq`，讓下次開機仍讀到舊槽
- [ ] 兩槽 CRC 都失敗時回到出廠預設，且**出廠預設是全部角色狀態良好**
- [ ] `size` 欄位小於當前結構大小時，未涵蓋的欄位以預設值補齊
- [ ] `version` 大於當前韌體版本時，拒絕載入而非誤讀（防止降級燒錄毀檔）
- [ ] 離線衰減計算有下限 30，且要防 `saved_at_unix` 在未來（RTC 亂掉時）
- [ ] 首次開機（兩槽皆空）時 `first_boot_unix` 要寫入
