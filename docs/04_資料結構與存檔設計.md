# 04 — 資料結構與存檔設計

第一版是純單機，所以「資料庫」在這個專案裡指的是**裝置端的三層資料結構**，
不是 SQL。ESP32 上沒有有意義的 SQL 資料庫，硬塞一個進去只會浪費 flash 與 RAM。

| 層 | 位置 | 生命週期 | 用途 |
|---|---|---|---|
| A 執行期狀態 | RAM | 開機到關機 | 遊戲邏輯讀寫的即時狀態 |
| B 存檔 | flash `savegame` 分區 | 永久 | 養成進度。**掉電絕不可損毀** |
| C 事件記錄 | LittleFS 環形檔 | 永久（滾動覆蓋） | 成長紀錄、除錯、未來的家長功能 |
| D 資產包 | flash `assets` 分區 | 燒錄時寫入 | 唯讀，`spi_flash_mmap` 直接定址 |

---

## A. 執行期狀態（RAM）

```c
typedef enum {
    CHAR_ICE_PRINCESS = 0,
    CHAR_CHIHUAHUA    = 1,
    CHAR_BROWN_MIXED  = 2,
    CHAR_BRINDLE_GUARD= 3,
    CHAR_COUNT        = 4
} character_id_t;

/* 需求值一律 0..100。用 uint8_t 而非 float：
   ESP32-S3 有 FPU，但存檔要 packed 且版本穩定，整數比較好對齊與遷移。 */
typedef struct {
    uint8_t hunger;      /* 飽足 */
    uint8_t energy;      /* 精力 */
    uint8_t mood;        /* 心情 */
    uint8_t bladder;     /* 如廁，僅狗 */
    uint8_t tidy;        /* 整潔，僅公主 */
} needs_t;

typedef struct {
    needs_t  needs;
    uint16_t affection;      /* 只增不減，上限 65535 */
    uint8_t  outfit_id;      /* 僅公主 */
    uint8_t  current_anim;   /* animation_id_t */
    uint16_t anim_frame;
    uint32_t anim_started_ms;
    int16_t  pos_x, pos_y;   /* 螢幕座標 */
    uint8_t  facing;         /* 0 = 面向右，1 = 面向左 */
    uint8_t  flags;
} character_runtime_t;

typedef struct {
    character_runtime_t chars[CHAR_COUNT];
    uint32_t  now_unix;
    uint8_t   night_mode;
    uint8_t   selected_char;   /* 目前被小孩點選的角色，0xFF = 無 */
    uint8_t   brightness;
    uint8_t   volume;
    bool      dirty;           /* 有未存檔的變更 */
    uint32_t  last_save_ms;
} game_state_t;
```

## B. 存檔

### 為什麼不用 NVS

NVS 可以用，但 blob 改寫較重，且磨損平衡的行為對我們是黑箱。
自管一個 8 KB 分區、手動做 A/B 雙槽，換來的是**可稽核的掉電安全性**——
這對一台會被 3 歲小孩隨手拔電的裝置是必要的，不是過度設計。

NVS 仍然保留，但只放設定值（亮度、音量），那些丟了無所謂。

### 結構

```c
#define SAVE_MAGIC    0x31544550u   /* "PET1" little-endian */
#define SAVE_VERSION  1
#define SAVE_SLOT_SZ  4096          /* 一個 flash sector */

typedef struct __attribute__((packed)) {
    needs_t  needs;
    uint16_t affection;
    uint8_t  outfit_id;
    uint8_t  unlocked_outfits;   /* bitmask */
    uint8_t  reserved[4];
} character_save_t;               /* 13 bytes */

typedef struct __attribute__((packed)) {
    uint32_t magic;
    uint16_t version;
    uint16_t size;               /* 本結構實際大小，用於版本遷移 */
    uint32_t seq;                /* 單調遞增。開機時選 seq 較大且 CRC 正確者 */
    uint64_t saved_at_unix;

    character_save_t chars[CHAR_COUNT];

    uint32_t total_feeds;
    uint32_t total_plays;
    uint32_t total_pets;
    uint32_t first_boot_unix;    /* 「我們認識多久了」 */

    uint8_t  brightness;
    uint8_t  volume;
    uint8_t  night_start_hour;   /* 預設 20 */
    uint8_t  night_end_hour;     /* 預設 7  */

    uint8_t  reserved[32];       /* 預留給未來欄位，避免馬上就要 v2 */
    uint32_t crc32;              /* 涵蓋本結構前面所有位元組 */
} save_blob_t;
```

### A/B 雙槽

```
savegame 分區 8 KB
├── slot A  offset 0      4 KB
└── slot B  offset 4096   4 KB
```

**寫入**：永遠寫進 `seq` 較小的那一槽（也就是較舊的），寫完驗證 CRC。
過程中掉電最多毀掉舊槽，新槽仍完好。

**讀取**：兩槽都讀，取 `magic` 正確、`crc32` 通過、`seq` 最大者。
兩槽都壞才回到出廠預設——而且**出廠預設是「四個角色都很開心」**，不是全部歸零。

### 寫入時機與 flash 壽命

| 時機 | 說明 |
|---|---|
| 定期 | 有 `dirty` 且距上次寫入 ≥ **300 秒** |
| 立即 | 進入 deep sleep 前、偵測到電量過低、解鎖里程碑、換裝 |

壽命估算：

```
每天寫入 ≈ 60 次（清醒 5 小時 / 300 秒 + 事件觸發）
雙槽交替 → 每槽每天 30 次
flash 耐久 100,000 次 ÷ 30 ≈ 3,300 天 ≈ 9 年
```

### 版本遷移

**改動 `save_blob_t` 的任何欄位都必須遞增 `SAVE_VERSION` 並寫遷移函式。**
小孩的養成進度不可以因為韌體更新就消失。這件事沒有商量餘地。

`reserved[32]` 的存在就是為了讓「加欄位」不需要換版本——
新欄位從 reserved 裡切，舊韌體讀到的是 0，新韌體讀舊檔也是 0，雙向相容。

## C. 事件記錄

固定長度記錄的環形檔，寫在 LittleFS。

```c
typedef enum {
    EV_BOOT = 1, EV_SLEEP, EV_WAKE,
    EV_FEED, EV_PLAY, EV_PET, EV_TOILET,
    EV_DRESS, EV_UNLOCK, EV_MILESTONE,
    EV_NEEDS_SNAPSHOT,      /* 每小時一筆，用於畫成長曲線 */
} event_type_t;

typedef struct __attribute__((packed)) {
    uint32_t ts;        /* unix time */
    uint8_t  type;      /* event_type_t */
    uint8_t  actor;     /* character_id_t，非角色事件填 0xFF */
    uint8_t  value;     /* 依 type 解讀，例如餵食回補量 */
    uint8_t  flags;
    uint32_t extra;     /* 依 type 解讀 */
    uint32_t reserved;
} event_rec_t;          /* 16 bytes，對齊友善 */
```

```
events.bin
├── header 16 B  { magic, version, capacity, write_index }
└── records      capacity × 16 B，寫滿後從頭覆蓋
```

`capacity = 8192` → 128 KB 檔案 → 以每天約 60 筆計，**約 136 天**的完整歷史。

用途：
- 未來若要做家長回顧（「這個月餵了幾次」），資料已經在了
- 除錯時可以重建小孩實際的操作序列
- `EV_NEEDS_SNAPSHOT` 讓「和牠們認識了 87 天」這種畫面有資料來源

**不含任何個人資料。** 只有時間戳與遊戲事件，沒有姓名、沒有位置、不連網。

## D. 資產包

```
assets.bin
├── header    { magic "IPA1", version, asset_count, index_offset, palette_offset }
├── index[]   { name_hash(u32), type(u8), flags(u8), w(u8), h(u8),
│               palette_id(u8), frame_count(u8), offset(u32), size(u32) }
├── palettes  每組 16 × RGB565（32 B），角色各一組
└── blobs     4bpp 索引點陣圖，逐張 RLE 壓縮
```

燒進 `assets` 分區後用 `spi_flash_mmap` 映射到位址空間，
index 可以直接當結構指標存取、零複製。sprite 用到時才 RLE 解碼進 PSRAM 的 LRU 快取。

**RLE 格式**（針對 4bpp 索引 + 大片透明區最佳化）：

```
每個 token 1 byte:
  0nnnnnnn          接下來 n 個像素是透明（n = 1..127）
  1nnnniiii         接下來 n 個像素都是索引 i（n = 1..15）
  超過 15 的同色連續 → 拆成多個 token
```

實測這種平塗、限色、大片透明的像素藝術，壓縮率約 **2.5–3×**。

## 完整性檢查清單

實作存檔層時逐項驗證，這些是掉電安全性的實際保證：

- [ ] 寫入前先 erase 目標 sector，寫完立刻讀回驗證 CRC
- [ ] 驗證失敗不更新 `seq`，讓下次開機仍讀到舊槽
- [ ] 兩槽 CRC 都失敗時回到出廠預設，且**出廠預設是全部角色狀態良好**
- [ ] `size` 欄位小於當前結構大小時，未涵蓋的欄位以預設值補齊
- [ ] `version` 大於當前韌體版本時，拒絕載入而非誤讀（防止降級燒錄毀檔）
- [ ] 離線衰減計算有下限 30，且要防 `saved_at_unix` 在未來（RTC 亂掉時）
- [ ] 首次開機（兩槽皆空）時 `first_boot_unix` 要寫入
