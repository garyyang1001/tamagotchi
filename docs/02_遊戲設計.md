# 02 — 遊戲設計

使用者：**3–5 歲**。這個年齡的設計約束比任何技術約束都嚴格，本文件先列約束再列機制。

---

## 一、設計約束（不可違反）

### 1. 沒有失敗狀態

| 傳統電子雞 | 本專案 |
|---|---|
| 疏於照顧 → 生病 → 死亡 | 需求歸零 → 角色安靜地播放「等待關心」動畫 |
| 紅色警告、閃爍、倒數 | 無警告色、無閃爍、無計時器 |
| 錯過餵食有永久後果 | 沒有永久後果 |
| 離線期間持續衰減到 0 | 離線衰減有下限（見下） |

理由：3–5 歲無法區分「遊戲角色的狀態」與「我做錯了事」。
死亡機制對這個年齡是真實的情緒事件，不是遊戲挑戰。

### 2. 離線衰減下限

小孩可能三天、一週沒碰這台機器。回來時不可以看到四個角色全部歸零。

```
離線時數 h：
  h ≤ 8   → 正常衰減
  h > 8   → 衰減速率減半
  任何需求的離線衰減下限 = 30
```

也就是說，不管離開多久，回來時每個需求至少還有 30/100，
角色是「有點想你」而不是「快撐不住了」。

首次開機且離線超過 24 小時時，開場播放 `happy_greeting` 而不是 `sad_waiting`——
**回來永遠是被歡迎的**。

### 3. 全圖示介面

- 任何操作都不需要閱讀文字
- 圖示最小 **48×48 px**（不是為了手指精度，是為了 3 歲要在一公尺外認得出來）
- 同一畫面最多 **3 個可選項**
- 每次按鍵在 **100 ms 內**必須有視覺回饋（游標移動 + 音效），
  即使實際動作要跑 2 秒

### 4. 情緒表現上限

- 難過的最強表現：耳朵下垂 + 眼神向下 + 動作變慢
- **不做**：哭泣、眼淚、發抖、蜷縮躲藏、痛苦表情
- 虎斑護衛犬**不露牙、不做攻擊姿態**。牠的守護感來自站姿與專注，不是威嚇

## 二、需求系統

每個角色有 4–5 項需求，範圍 0–100，初始 80。

| 需求 | 適用 | 每小時衰減 | 說明 |
|---|---|---|---|
| `hunger` 飽足 | 全部 | −4 | 餵食回補 |
| `energy` 精力 | 全部 | −3（清醒）/ +12（睡眠） | 睡覺回補 |
| `mood` 心情 | 全部 | −3 | 撫摸、陪玩回補 |
| `bladder` 如廁 | 三隻狗 | −5 | 帶去廁所回補 |
| `tidy` 整潔 | 公主 | −2 | 換衣服回補 |

另有一項**只增不減**的 `affection`（好感度），累積所有互動次數。
它不會衰減、沒有上限行為壓力，純粹是「我們一起相處了很久」的紀錄。
達到里程碑時解鎖服裝或新動畫。

### 衰減曲線

線性衰減，每 5 分鐘結算一次。以每小時 −4 計算，
`hunger` 從 100 掉到 30 需要 **17.5 小時**——大約是一天一次的照顧節奏，
不會造成「一直被機器催」的壓力。

### 需求對應的表現

| 區間 | 角色表現 |
|---|---|
| 70–100 | 正常待機動畫，偶爾主動做開心動作 |
| 40–69 | 待機動畫頻率降低，偶爾看向對應的物件（飯碗 / 床 / 門） |
| 0–39 | 播放對應的「等待關心」動畫，圖示上出現柔和的小提示（非紅色） |

需求為 0 時**不再有任何額外變化**。0 和 39 的表現是一樣的，只是動畫頻率不同。

## 三、互動

### 主畫面

房間場景，四個角色同時在畫面中。改用真像素風之後四角色同框只佔 254px，
放得進 320 寬，**不需要兩套縮放**（見 `docs/03` 修訂 R1）。

小孩用**三顆實體按鍵**操作：

```
   ◀ 上一個        ● 確認        ▶ 下一個
```

**主畫面**：冰雪公主常駐，加上**最多一隻**被呼叫出來的狗。
游標停在「房間裡真的看得見的實體」上，由 `game_main_slot_count()` 決定有幾格：

| 游標位 | 按確認會怎樣 |
|---|---|
| 🚪 門 `SLOT_DOOR` | 開呼叫選單（三隻狗三選一）。**有狗在場時也是同一個選單**——換狗不必先送回去 |
| 👗 衣櫃 `SLOT_WARDROBE` | 進換裝畫面 `UI_DRESS` |
| 💡 開關 `SLOT_LIGHT` | 直接切燈，不進選單。**「休息」不是動作，就是關燈** |
| 👸 公主 `SLOT_PRINCESS` | 進互動選單（4 個，她沒有 bladder） |
| 🐕 狗 `SLOT_DOG` | 進互動選單（5 個）。**只在有狗在場時才存在這一格** |

游標停在公主或狗身上時，**不必按任何鍵就直接顯示那個角色的進度條**
（`game_need_bars()`）。少一層導覽，而四歲半看得懂條狀圖。

**互動選單**：固定 5 個大圖示（公主 4 個）。

```
  🍚 吃飯    🎾 玩    ✋ 摸摸    🛁 洗澡    🚽 上廁所
```

左右鍵移動、確認鍵執行，執行完自動回主畫面。

> **2026-08-02：從「需求驅動的前三名」改成「固定 5 個」。**
>
> 舊版每次只顯示最需要的三個，理由是三歲同一畫面最多 3 個可選項。
> 使用者的女兒現在**四歲半、快五歲**，明確同意認知難度可以再完整一點。
>
> 尺寸上本來就放得下：320 ÷ 5 = 64 px，48 px 的圖示還有餘裕——
> 擋住的一直是認知負荷不是空間。
>
> 固定不變的另一個好處是**位置可預期**：她記得住「洗澡在右邊數來第二個」，
> 而動態替換的版本每次打開位置都不一樣。
>
> `game_suggest_actions()` 因此改變職責：不再決定「顯示哪幾個」，
> 改成回報「哪一個最需要」，讓渲染層在那個圖示上加提示。
>
> **「沒有失敗狀態」不跟著放寬。** 進度條低的時候不變紅、不閃、不倒數，
> 只是短一點；離線衰減下限 30 還在，所以條子永遠不會空。

**呼叫寵物**：一次只能有一隻狗在房間裡。要換就直接呼叫新的，
**舊的自己從門走回去**（`ANIM_WALK`，不是 `ANIM_SAD_WAIT`——牠不是被趕走）。
兩段過場同時跑（`ARRIVE_MS` / `LEAVE_MS` 各 1200 ms）。

多一個「先送回去」的步驟對四歲是多餘的負擔，而且會讓「換一隻」變成兩件事。

**不在場的狗仍然會餓，但速率減半**，下限一樣是 `OFFLINE_DECAY_FLOOR`（30）。
牠們是在別的房間過自己的生活，不是不存在。完全凍結的話小孩就沒有理由
去叫另外兩隻出來；減半 + 下限 30 則保證不會有壓力。

**沒有取消鍵。** 3 歲不該被要求學會「返回」這個抽象概念——
選單 8 秒沒有任何按鍵就自己回主畫面（`MENU_TIMEOUT_MS`）。

**選單一打開，圖示就固定住。** 需求會隨時間變化，如果選單開著的時候
某個需求跨過門檻，圖示會在小孩眼前跳掉——她伸手要按的東西變成別的了。
`game.c` 在進選單的當下抓一份快照。

第四個動作依角色狀態動態替換：
- `energy < 40` 或夜間 → 🛏️ 睡覺
- `bladder < 40`（狗）→ 🚪 出去
- `tidy < 40`（**四個角色都有**）→ 🛁 洗澡

> **2026-08-02 修訂**：`tidy`（整潔）原本只給公主、而且對應「換衣服」。
> 加了洗澡之後放寬給四個角色——狗也要洗澡，而且存檔不用遷移
> （`save.c` 本來就把四個角色的 `tidy` 都初始化成 80）。
>
> **換衣服（`ACT_DRESS`）不再是需求驅動的。** 服裝是 affection 里程碑的獎勵，
> 小孩想換就換，不該因為「公主髒了」而跳出換衣服的圖示。

**五個圖示固定顯示、位置固定不動。** 需求只決定**哪一個被標記成「現在最需要」**
（`game_suggest_actions()`），不決定顯示哪幾個。位置可預期比資訊密度重要——
四歲半記得住「洗澡在右邊數來第二個」，而動態替換的版本每次打開位置都不一樣。

### 互動流程（以餵食為例）

```
選「餵食」按確認
  ↓ 100ms 內：圖示放大 + 「叮」音效
播放 eat（吃）                  4 格，循環 2 次
播放 eat_happy（吃飽開心）       6 格
  ↓ 同時：真實狗叫聲 / 咀嚼音效
hunger += 35，mood += 5
回到待機
```

總時長約 2.5 秒（權威定義在 specs/animations/<char>.anim.json，本文只描述意圖）。這是幼兒注意力的合理長度——夠長到有「發生了一件事」的感覺，
短到不會失去耐心。**不可以做需要等待 10 秒以上的動畫。**

### 撫摸

選「摸摸」之後角色播 `pet_react`，愛心浮在頭上。
**確認鍵可以一直按，想摸幾次就摸幾次**——它沒有目標、沒有結束條件。
每一次 `mood += 3`、`affection += 1`。

> **2026-08-02 修訂**：原本寫的是「進入撫摸模式，小孩用手指在角色身上**滑動**，
> 角色跟著滑動位置播放對應反應」。那是**觸控時代的設計**，改成三顆實體按鍵之後
> 根本做不到——沒有手指位置這個輸入。
>
> （這一段在把「觸控」二字全面清掉的那一輪漏掉了，因為它寫的是「滑動」不是「觸控」。
> 找過時的設計不能只搜關鍵字，要讀。）
>
> 換成按鍵之後反而更符合規則 1 的精神：**沒有模式就沒有「怎麼離開」的問題**，
> 三歲到五歲都不必學會退出。「摸摸」和其他四個動作在結構上完全一樣，
> 只是它可以無限重複。

## 四、時間與夜間模式

**真實時間**，不加速。角色的作息和小孩同步。

| 時段 | 行為 |
|---|---|
| 07:00–19:30 | 正常 |
| 19:30–20:30 | 畫面色調漸暗，角色開始打呵欠，動畫速度降到 0.7× |
| 20:30–07:00 | 角色全部睡著，畫面很暗，只有呼吸動畫。按鍵只會讓角色翻個身 |

夜間模式是刻意的**家長功能**：機器自己睡了，小孩比較容易接受該睡覺了。
時間可在設定中調整。

> **2026-08-02 修訂**：判定改成 `night = 時鐘夜間 || 電燈關著`。
> 小孩自己按主畫面第 5 格把燈關掉時，表現與時鐘夜間完全一樣，
> 而且**沒有任何數值後果**，再按一次就全部復原。見第 10.5 節。

離線期間的睡眠也計算 `energy` 回補——晚上關機不會被懲罰。

## 五、角色個性差異

同樣的互動，四個角色的回應動畫不同。這是讓角色「是牠們自己」的關鍵。

| 互動 | 吉娃娃 | 棕色米克斯 | 虎斑護衛犬 | 公主 |
|---|---|---|---|---|
| 餵食 | 興奮跳、吃很快、找更多 | 眼睛發亮、狼吞虎嚥、舔碗 | 先坐好等許可、才慢慢吃 | 優雅地吃、吃飽笑 |
| 摸摸 | 整隻黏上來、要抱 | 翻肚子要摸肚 | 瞇眼、尾巴慢搖 | 微笑、害羞 |
| 玩球 | 快速衝、原地轉圈 | 慢慢走過去、叼回來 | 空中接球、跑大圈 | 丟球、拍手 |
| 閒置久 | 一直看著公主 | 趴下睡著 | 巡邏、看門口 | 坐椅子看書 |

### 角色專屬行為

- **吉娃娃**：`cling_to_princess`（黏著公主）、`jealous`（別的狗被摸時吃醋）
- **棕色米克斯**：`hungry_stare`（飢餓時定定看著你）、`comfort_princess`（公主難過時靠過去）
- **虎斑護衛犬**：`check_room`（定時巡邏）、`guard_princess`（有動靜時擋在公主前面）

這些是**自發行為**，不需要小孩觸發，隨機在待機時播放。
它們是讓機器「活著」的來源。

## 六、進度與解鎖

沒有分數、沒有等級、沒有排行。只有 `affection` 里程碑：

| affection | 解鎖 |
|---|---|
| 100 | 公主服裝：睡衣 |
| 300 | 公主服裝：粉紅裙 |
| 600 | 群體動畫：全家福合照 |
| 1000 | 公主服裝：冬季裝 |
| 1500 | 群體動畫：一起睡覺 |
| 2500 | 公主服裝：守護者裝 |

解鎖時播放一段慶祝動畫。**沒有任何東西會被鎖回去或失去。**

## 七、音效

| 類型 | 來源 | 說明 |
|---|---|---|
| 狗叫 / 呼嚕 / 喘氣 | **錄真實的三隻狗** | 這是本專案的情感核心，值得花時間錄 |
| 腳步 / 吃東西 / 玩球 | 合成或素材庫 | |
| UI 回饋音 | 合成 | 短、柔和、非電子感 |
| 環境音 | 可選 | 房間的安靜底噪 |

**錄音建議**：手機錄 48 kHz WAV，每隻狗錄叫聲 3–5 種語氣（開心、警戒、討食、想睡），
每種 3–5 次取最好的一次。裝置端轉成 **16 kHz 單聲道 IMA-ADPCM**（約 4:1 壓縮），
單個 1 秒的叫聲約 8 KB，全部音效控制在 500 KB 以內。

## 九、有實證支持的幼兒約束

> **2026-08-02**：本專案從觸控改成三顆實體按鍵。這一節的六個小節裡，
> 只有 9.2 與 9.4 是輸入方式相關的，已改寫成按鍵版；
> 9.2 的毫秒數字保留但明確標示「那是在觸控螢幕上量的」，不當成按鍵的證據。
> 其餘四節（因果歸因、序列可打斷、虛擬寵物死亡、不成立的說法）與輸入方式無關，原樣保留。

以下每一條都來自同儕審查文獻或可查證的一手資料。
**標示為「無實證」的項目，是我們自己的判斷，不要當成研究結論引用。**

### 9.1 因果歸因的方向是反的（與輸入方式無關）

一般直覺是「回饋太慢，小孩會感覺不到因果」。實際風險相反——**他們會過度歸因**。

> 兒童會表現出魔法思維，把同時發生的事件關聯成因果關係，即使兩者無關……
> 設計者必須小心應用程式在孩子觸碰螢幕的當下所決定執行的動作；
> 例如，在顯示某個背景獨立程序的結果之前，先等待一段時間。
> — Vatavu, Cramariuc & Schipor 2015, *Int. J. Human-Computer Studies* 74:54–76
> （n=89，3–6 歲，文獻中最大的兒童觸控資料集）

**這是排程約束，不是延遲約束。**

實作：`POST_INPUT_QUIET_MS = 2500`。**任何按鍵**之後 2.5 秒內不觸發自發行為。
否則小孩剛摸完狗、狗就自己播 `sad_wait`，她會認為是自己弄的。

這一條和輸入方式無關——改成按鍵之後只換了常數名稱。

### 9.2 一次按壓可以長達 5 秒

| 量測 | 3–6 歲 | 成人 |
|---|---|---|
| 單次點擊接觸時間 | 267–312 ms | 53 ms |
| 最長點擊（未滿 4 歲） | **5.1 秒** | — |
| 最長點擊（4–5 歲） | 4.2 秒 | — |

同來源。

> **這組數字是在觸控螢幕上量的。** 本專案改用實體按鍵之後不能直接把毫秒數
> 當成按鍵的證據。但「這個年齡按下去會按很久、而且那對她只是**一次**」
> 這個行為觀察是可以帶過來的——它講的是手指的運動控制，不是螢幕。

實作要求（`firmware/include/game.h` 的 `game_button()` 契約）：

- **按下的當下呼叫，不是放開時**（Sesame Workshop 2012）
- **一次按壓只呼叫一次。不可以做長按自動重複**——
  她按住 5 秒，對她只是按了一下，自動重複會讓游標飛過去
- 按住超過 1–2 秒時給一個回饋，讓她知道可以放開了
- **不要用雙擊**，小孩會以為程式沒反應

### 9.3 序列必須可被打斷

> 學齡前兒童即使被明確告知不要點，仍會在非互動段落點擊 38–44 次。
> — Russo-Johnson et al. 2017, *Frontiers in Psychology*（n=170，2–4 歲）

點擊是**優勢反應**（prepotent response），擋不住。唯一的問題是我們要不要理它。

實作：`game_do_action` 在序列播放中**可以被打斷**。需求值本來就夾在 100，
重複觸發不會有任何負面效果。

上限參考 WCAG 2.2.2：自動播放且超過 5 秒的動畫必須提供暫停手段。
我們的互動序列約 2.5 秒，且全部可打斷。

### 9.4 發光／脈動的可點提示對這個年齡無效

> 視覺狀態變化（發光、脈動、縮放）在 2–5 歲各年齡層都無效，
> 但它出現在超過 40% 的已上架學齡前 app 中。
> — Hiniker et al., ACM IDC 2015（n=34，2–5 歲；先審查了 100 個學齡前 app）

同研究：3 歲時只有不到 30% 能理解語音／手勢示範提示，3.5 歲躍升到約三分之二。
**先前的觸控經驗與理解能力無關。**

實作：**按鍵介面根本沒有這個問題**，而這是選按鍵而不選觸控的主要理由之一
（見 `docs/01` 的「為什麼不用觸控」）。
觸控介面必須解決「小孩怎麼知道哪裡可以點」，而這個年齡讀不懂任何提示；
按鍵介面只要有一個會動的游標，左右鍵和游標之間是直接的因果。

仍然成立的部分：**不要用發光／脈動來表示「這個可以選」**，
選取狀態要用位置（游標在哪）而不是用光效。

### 9.5 虛擬寵物死亡

- Bandai **自己**把死亡表現從墓碑與日本幽靈改成天使光環、化為星塵，
  說明文字改為「回到宇宙」（Dodd, Fowler & Lottridge 2025, *Entertainment Computing*）
- 1997 年香港青年協會確實在 24 小時熱線加入電子雞輔導服務（南華早報 1997/5/30）

⚠️ **但要誠實**：**沒有任何流行病學或實驗研究測量過電子雞死亡對兒童的傷害。**
1997 年的報導記錄的是「服務被提供」，不是「傷害被測量」。

我們的「無死亡」規則有**設計先例**支持（Bandai 自己改了），
但不要宣稱它有**實證傷害研究**支持。

相關但方向相反的證據：UCLA 2025 的 Daniel Tiger 回溯調查顯示，
最令人印象深刻的內容正是悲傷、憤怒、挫折——**前提是同時給了應對策略**。
所以問題不在於呈現負面情緒，而在於呈現負面情緒卻沒有出路。

### 9.6 不成立的說法（不要引用）

研究過程中查證發現，以下廣為流傳的數字**在原始文件中不存在**：

| 說法 | 狀態 |
|---|---|
| 「Sesame Workshop：延遲 0.5 秒小孩就會重複點擊」 | **原文沒有這句**，是設計部落格加上去的 |
| 「Sesame Workshop：手勢示範必須在 1 秒內完成」 | **原文沒有這句** |

**不是兒童專屬研究**。它仍然是好規則，但不要宣稱有兒童實證。

## 十、畫面狀態機

> **2026-08-02 新增。** 改成三顆實體按鍵之後，韌體只有 `UI_MAIN` 與 `UI_MENU`
> 兩個畫面，開機／關機／待機／燈／電量／里程碑六件事沒有任何狀態去接。
> 這一節補齊。權威定義在 `firmware/include/game.h` 的 `ui_screen_t`，
> 本節描述意圖與理由。

### 10.1 七個畫面

```
  （上電）
     │
     ▼

│ UI_MAIN  │◀──────────────────────────────────────│            │ 未解鎖的不顯示
```

**呼叫與換狗的過場不是畫面**，是 `UI_MAIN` 底下的一個狀態
（`game_pet_transition()`）。過場期間不接受互動，但按鍵可以立刻把它走完。

### 10.2 開機 `UI_BOOT`

存檔載入通常只要幾十毫秒。不設下限的話，開機圖會一閃而過——
對 3 歲那不是「機器開起來了」，是「機器閃了一下」。
所以離開條件是**兩個都要成立**：外層呼叫過 `game_boot_done()`，且已經停滿 1200 ms。

離線超過 24 小時的歡迎動畫（第一節第 2 點）**在離開 BOOT 時才從第 0 格起跑**。
`game_init` 就把它擺好了，但那半秒會被開機圖蓋掉；重播一次，整段才落在主畫面上。
**回來永遠是被歡迎的**，這件事不能被開機流程吃掉。

### 10.3 關機 `UI_POWEROFF`

電源鍵是獨立的第四顆鍵，長按由外層判定後呼叫 `game_power_off()`。
**`game.c` 裡沒有任何長按計時**——三顆操作鍵一律沒有長按自動重複（第 9.2 節）。

關機**不可以看起來像壞掉或消失**。四個角色立刻播 `sleep_breathe`，
螢幕維持全亮，兩秒之後外層才真的斷電。這裡刻意**不插姿態過渡動畫**：
站→坐→趴要 2.25 秒，比 2 秒還長，小孩會看到大家「正要躺下」的時候螢幕就黑掉。

**按任何一顆操作鍵都取消關機**，回主畫面並播醒來的序列。
3 歲很容易誤觸電源鍵，這條路必須救得回來，而且要看得出來自己救回來了。

### 10.4 待機（背光，不是畫面）

`game_backlight()` 回傳 0..100，`game_should_sleep()` 告訴外層何時進 light sleep。

| 距上次按鍵 | 背光 | 說明 |
|---|---|---|
| < 60 秒 | 100 | |
| 60 秒 – 10 分鐘 | 50 | **動畫繼續跑** |
| > 10 分鐘 | 0 | `game_should_sleep()` 為真，外層進 light sleep |

任何按鍵立刻回到 100。開機圖與關機圖期間強制 100（那兩段畫面就是要給人看的）。

**變暗不是暫停。** 小孩會純粹坐著看四隻狗自己動，那是這台機器的主要內容之一；
把「在看」誤判成「沒在用」而停掉動畫，等於把最好的部分關掉。
`docs/01` 原本的 30 秒／3 分鐘是**觸控時代**的政策（手離開螢幕就等於沒在用），
已作廢，理由同上。

### 10.5 電燈（主畫面游標的第 5 格）

主畫面的游標從 4 格變 5 格：四個角色 + 一個電燈開關（`SEL_LIGHT`）。
游標停在電燈上時沒有選取任何角色（`selected == CHAR_COUNT`），
在那裡按確認**不進選單**，直接切換開關——多一層選單對 3 歲就是多一個學不會的步驟。

夜間判定改成：

```
night = 時鐘夜間（night_start_hour ~ night_end_hour）  ||  燈關著
```

兩者的畫面表現一樣（變暗 + 動畫 0.7×  + 角色睡著），差別只在誰決定的：
一個是家長設的作息，一個是小孩自己按的開關。

**關燈不扣任何分、不觸發任何負面狀態、不會讓任何已解鎖的東西失去。**
再按一次燈就全部復原，角色播醒來的序列。

存檔上存的是 **`light_off`（0 = 燈開）不是 `light_on`**，放在
`save_blob_t.reserved[0]`（`SAVE_RSV_LIGHT_OFF`）。
理由是相容性不是風格：`reserved` 的契約是「新韌體讀舊檔得到 0」，
所以 0 必須代表舊韌體的行為，而舊韌體沒有電燈、螢幕永遠亮著 = 燈開。
存成 `light_on` 的話，既有機器一升級讀到 0 就是「燈關」，
小孩一開機看到全黑的房間，而且不知道那是可以按回來的。
存成 `light_off` 就沒有這個問題，**因此不需要遞增 `SAVE_VERSION`**。

### 10.6 電量

`game_set_power(percent, charging)` 由外層回報，狀態存在 `game_t`，**不進存檔**。
`game_power_hint()` 回傳 `PWR_NONE` / `PWR_CHARGING` / `PWR_LOW`（≤20%）/ `PWR_CRITICAL`（≤5%）。

**低電量在這台機器上不是失敗狀態。** 它不會讓角色難過、生病、變慢，
不觸發倒數、不扣需求值、不影響動畫、不影響畫面狀態。
它只是一個角落的圖示——「該找爸爸插電了」，而那是大人的事。
充電中優先於低電量：插著電就不必再提醒。

電量還沒被回報之前預設 100%，否則開機那一瞬間會顯示一個不存在的壞消息。

### 10.7 里程碑 `UI_CELEBRATE`

`affection` 跨過門檻（第六節）時進入慶祝畫面，四個角色播 `happy`，
3 秒後**自動**回主畫面。按任何鍵可以提前結束；
慶祝期間的按鍵**不執行任何選單操作**——那個畫面上的按鍵不該順手把某個動作也做掉。

「自動結束」是硬性的：不可以要求 3 歲學會「關掉這個畫面」。

**已經領到手的里程碑不會重新慶祝。** `game_init` 依存檔裡的 `unlocked_outfits`
先把 `unlocked_mask` 填好，否則每次開機都會把小孩早就拿到的東西重新算成新解鎖，
她每次開機都要看一次同樣的慶祝畫面。

### 10.8 這一節的規則 1 檢查

`firmware/test/test_game.c` 對上面六件事各有一組測試，其中守規則 1 的斷言是：

- 關機前後四個角色的需求值**逐 byte 相同**
- 關燈再開燈之後，需求值、`affection`、`unlocked_outfits` 一項都沒少
- 1% 電量跑 60 秒，存檔與滿電那台**逐 byte 相同**，動畫與畫面狀態也相同
- 慶祝前後需求值不變
- 舊存檔（`reserved` 全 0）升級之後**燈是開的**，角色不會一開機就全部睡著
