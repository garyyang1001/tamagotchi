## 二、已驗證的結論

這些是實測出來的，不是推論。它們推翻了原始規劃的多個假設。

### 2.1 影像模型的能力邊界

| 能做 | 不能做 |
|---|---|
| 造型設計、體型比例 | 產出乾淨的像素網格 |
| 大面積配色、標記位置 | 打準指定顏色 |
| 剪影與辨識特徵 | 控制 5 像素以下的特徵 |
| 部件分解圖（部件是獨立大圖） | 維持跨姿勢的角色一致性 |

**實測數據：**

```
宣稱「乾淨的像素網格、10 色」
實得  27,990 色、色塊長度 2/3/4/5 混雜、
      「純洋紅」背景是 #F703F5 / #F803F5 / #F702F5… 十幾種雜訊值

要求「眼睛放大 20%，虹膜與高光都要讀得出來」
實得  3×2 像素的純暗色塊，沒有虹膜也沒有高光

要求「去飽和的灰白吻部，almost silver-grey」
實得  飽和度 80 的暖褐色（目標是 26）

指定  1024×1024
實得  1341×1173
```

**對策**：全部在下游修，不要重生。`--remap` 把飽和度 80 修成 26，
`pixedit.py` 手工畫眼睛。分工是固定的，見 `CLAUDE.md` 規則 2。

### 2.2 換姿勢會造成身分漂移

以已核可的 master 為參考圖，明確要求「這是同一隻角色的不同姿勢，
不要重新設計、不要變得更可愛更年輕」，生成三個姿態：

| 姿態 | 結果 |
|---|---|
| 坐姿 | 變圓變幼，灰白吻部退回暖褐 |
| 趴姿 | 同上 |
| 正面 | 徹底的重新設計，眼睛變成褐色圓環 |

三張朝**同一個方向**漂移，這是系統性的。

**對策**：只生站姿的部件分解圖，其餘姿態由部件推導。
附帶收益：部件分解圖從三張降為一張。

### 2.3 拆開來畫，模型就做得到

同一個模型，在**組裝好的圖**上畫不出 3 像素的眼睛，
但在**部件分解圖**上（眼睛是獨立的大圖）就正確畫出了琥珀虹膜與白色高光。

這解釋了為什麼部件路線不只是為了動畫——它也提升了美術品質的上限。

### 2.4 語意重映射不能用數值距離

把手工調色盤用「最近 RGB 距離」套到 AI 產出上：
狗身上的中棕色像素因為數值上離 `muzzle_grey_dark` 比離 `coat_mid` 更近，
**整片肚子和腿被吸成灰白色**。

而且同一個來源色在不同部位有不同語意——AI 在吻部和小腿用了同一個 `#D0A980`，
整張圖一起 remap 會讓腳跟著吻部一起變灰。

**對策**：`--remap` 用人工填寫的語意對照表，並支援 `bbox` 區域限定。

### 2.5 Tier 0 的真實範圍比想像小很多

原本宣稱 21 個動畫都能用整隻 sprite 的變換做出來。錯了。

| 錯誤 | 實際效果 |
|---|---|
| `sit_down` 用 `scale_y: 86%` | 讀起來是狗被壓扁，不是狗坐下 |
| `eat` / `pet_react` 用 `rot: 4°` | 64px 上旋轉產生歪斜鋸齒，破壞像素網格 |
| `turn` 用 `scale_x: 40%` | 狗被橫向壓扁，不是轉身 |

**坐姿是不同的剪影，不是同一個剪影變矮。**

重新劃線後只有 **5 個**動畫符合 Tier 0：
`idle_breathe` `walk` `turn` `happy` `sad_wait`。

Tier 0 現在只允許**整數像素位移與水平翻轉**。

### 2.6 測試抓到的、在板子上很難發現的 bug

| Bug | 症狀 |
|---|---|
| `now_unix += dt_ms / 1000` | 100ms 步長時整數除法恆為 0，時鐘完全停住，夜間模式永不觸發 |
| 里程碑 `1 << m` | bit 0 是預設服裝，第一個里程碑等於什麼都沒給 |
| `apply_decay` 用函式靜態計數器 | 多個 game 實例互相污染 |
| `sad_wait` 機率 `50 + (40-low)` | 需求全零時 90% 時間垂頭喪氣，對 3 歲太沉重（已壓到 57%） |
| `cutparts` 投影分割 | 兩個部件投影重疊，16 個只切出 15 個 |
| `cutparts` 列分組用 `y0 // 門檻` | 矮部件（尾巴）上緣位置低，被誤分到下一列 |
| `cutparts` 用外接框裁切 | 帶走鄰近部件探進框內的像素 |
| 去背只靠色度門檻 | 邊緣殘留 562 px 洋紅混色（已加去溢色，歸零） |

### 2.7 端到端跑完之後才看得到的四件事

21 個動畫全部烘出來、放在同一張接觸表上比對之後，浮出四個之前看不到的問題。
全部有數字，全部記在 `build/preview/_REPORT.md`。

**(1) 階段 A 的角色比 master 小了一半 —— 這是最嚴重的一件事**

| 來源 | 尺寸 | 不透明像素 |
|---|---|---:|
| master sprite（5 個 transform 動畫用） | 64 × 54 | 1,809 |
| 階段 A 的 stand（16 個 rig 動畫用） | 43 × 41 | 914 |

同一隻狗在 `idle_breathe`（master）與 `idle_blink`（rig）之間切換時會**當場縮水
三分之一**。原因是部件在 `art/rigs/` 的原生解析度偏小，擺進 1344×1176 只佔到
約 903×861。修法是階段 A 把部件整體放大約 1.5 倍（階段 A 允許重新採樣），
或反過來把 master 重做成與部件同尺度。

同一個根因也吃掉了辨識特徵：rig 姿勢缺 `eye_dark`、`eye_highlight`、`tan_dark`
三個色階，**眼睛沒有瞳孔也沒有高光**，臉在 1× 下讀不出來。

**(2) lie 姿勢的脖子有 0 px 餘裕**

實測掃描 head 圖層在 lie 姿勢的所有 `dx`（−3..+3）× `dy`（−4..+4）組合：
只要 `dy ≤ −1`，整顆頭就與身體斷成兩個連通區域，`dx` 完全不影響。
`lie_down` f2 與 `wake_up` f1 原本各抬頭 2 px，畫面上是一顆浮空的頭。
已改成 `dy = 0`，代價是「頭尚未落定」那一拍沒了。

lie 姿勢另外還有一個 6 px 寬的洞（第 46–51 列的 x35–40），前腿與胸口分離，
高解析原圖就是分離的。

**(3) 尾巴往左抬就會脫離身體**

`tail` 的 z 最低（10），尾根靠鑽進軀幹裡藏起來。`tail_wag` 的作者量過這件事並
寫進 `_note`，但 `play_bow` f2（−1,−2）與 `chase_ball` f2（−2,−2）都往左移，
兩格各產生一條 35 px 的浮空尾巴。已分別改成 (+1,−2) 與 (0,−2)。

**(4) 64×56 的畫布沒有上下餘裕**

master 是 64×54、底部對齊，頭上只剩 2 列。`happy` 原本跳 7 px，
第 1–3 格共 141 px 被切掉，切的正好是頭頂與耳尖。已把幅度砍到 2 px——
**不會再切到頭，但 2 px 的彈跳表達不出「開心」，這是目前最弱的一支動畫。**
`sad_wait` 是同一個根因的下緣版本，四格共 38 px 的腳掌被切掉（未修）。

> 三個 `--check` 也順手證實了一件好事：三個姿勢**確實是不同的剪影**，
> 不是同一個剪影變矮。stand↔sit 的 IoU 0.643、stand↔lie 0.295、sit↔lie 0.356。

### 2.10 死程式碼比沒有程式碼危險

部件旋轉路線於 2026-08-01 移除，但只刪了 `assemble.py` / `cutparts.py` /
`specs/poses/` / `art/rigs/`。`bake.py` 裡的 `rig` 型、`LayerCache`、
七圖層群的疊合順序推導——共 244 行——留著沒動，因為「它又沒壞」。

代價在 2026-08-02 才顯現：

* `bake.py` 的模組 docstring 有一半在講「階段 A / 階段 B」，
  讀的人會以為那條路還在
* `test_bake.py` 的 25 項測試**全部**寫在 rig 型上。移除 rig 之後一項都跑不動——
  等於整個烘焙器有一整天是沒有測試的
* **frames 型從來沒有影格尺寸檢查**。原本那個檢查在 `LayerCache` 裡，
  只保護 rig 型。尺寸不符的影格會被默默貼在畫布左上角，
  畫面上看起來只是「動畫抖了一下」，很難回推原因

第三項是重寫測試時才抓到的——把測試從 rig 夾具改寫到 frames 夾具，
第一次跑就紅了。這是「測試不是為了證明程式對，是為了在改動時抓到你沒想到的洞」
的實例。

清理之後：`bake.py` 996 → 752 行、測試 25 → 28 項、
四個角色的 84 個 spritesheet **雜湊完全相同**（重構沒有改變任何產出）。

### 2.9 量化會吃掉小特徵，要在量化前保護

k-means 是照**面積**分色群的。淡藍眼在原圖只佔 0.06%，永遠拿不到自己的一群，
必然被併進附近的大色塊。

實測後果：`brown_mixed` 的 master 有眼睛（那是 `patch.json` 手工補的），
**15 個動畫全部沒有眼睛**——狗一走路就沒眼睛了，而且一直沒被發現。

修法是繞過量化：在原圖用色相抓出目標像素，用同一組格線降採樣成遮罩，
最後直接蓋上調色盤的角色色。規則寫在調色盤的 `protect` 段。

保護要在 **`cutstrip.py`** 就生效，不能只在 `pixelate.py`：
cutstrip 在切開之前會先把整張圖量化到 16 色，色相在那一步就死了。

驗證這件事有沒有真的成立，看閉眼的動畫就知道——
`idle_blink` 逐格虹膜 4→3→0、`yawn` 7→1→0→0、`pet_react` 4→0→0→4、
`sleep_breathe` 全 0。它追的是真實的眼睛狀態，不是無腦蓋色。

附帶的第二條規則 `min_thickness`：模型很愛沿著腿的輪廓補一條 1px 寬的粉線
（它以為那是背帶的帶子），降到 64px 讀起來是「狗穿粉紅襪子」。
提示詞明確禁止過一輪仍然有一半的圖會畫，所以改在管線擋：
只保留屬於某個 2×2 全命中方塊的像素。實測乾淨的圖只掉 5-13%（外緣），
畫壞的掉 48-53%（就是那些腿線）。**不要**套在眼睛上——那才 2px，會整個消失。

### 2.11 直覺說 per-sheet 比較小，量出來是它大 25%

`pack.py` 唯一需要「量了才能決定」的事：blob 的單位是每格影格還是每張 spritesheet。
兩種都實作、都量（`--blob-unit` 可以切換，每次執行都印對照表）：

| 方案 | 全部 blob | 壓縮率 | 解一格要解碼的像素（平均／最大） |
|---|---:|---:|---:|
| 每張 spritesheet | 257,718 B | 2.89× | 15,690 / 36,864 |
| 每格影格 | 272,258 B | 2.74× | 3,993 / 6,144 |
| **每格影格 + 相同 blob 去重** | **204,908 B** | **3.64×** | **3,993 / 6,144** |

直覺是對的：一列橫跨四格，透明 run 可以接起來，per-sheet 確實小 5.3%。
**但那個優勢被去重整個吃掉還倒賠。**

原因是 `transform` 型動畫（呼吸、難過等待、跳躍）把位移記在 `screen_dy` 而不是
畫進像素裡——同一個動畫的每一格是**逐位元相同的點陣圖**。
`ice_princess/happy` 六格全部指向同一個 1,042 B 的 blob，只有 `screen_dy`
是 0/−5/−9/−9/−4/0。365 格裡只有 280 格是唯一的，去重省 24.7%。
而去重只有在 blob 是「每格」時才做得到：blob 是整張 sheet 的話，四格黏在一起。

決定性的那一項其實不是大小，是解碼成本：渲染層一次只畫一格，
per-sheet 要多解 **3.93 倍**的像素、佔 3.93 倍的 PSRAM
（公主一張 sheet 是 36,864 px，一格只要 6,144）。兩個軸都輸。

> 這條和 2.7 是同一類：**端到端組完、把數字並排印出來，才看得到的東西。**
> 這一次是在寫 `pack.py` 之前就先量了，而不是事後才發現。
